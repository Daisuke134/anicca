### C3 — Route cache (F2)
- **AS-BUILT (origin/main, verified 2026-07-04)**: the cache is an **in-process `Map()` with a 10-min TTL** — `travel.js:14` `makeRouteCache({ store: new Map(), ttlMs: 10*60_000 })`, keyed on `(from_geo, to_geo, time_bucket)` (`route-cache.js`). This DIRECTLY kills the dominant cost: the 60-sec scheduler tick was recomputing the SAME route ~30×/event within ONE long-lived Railway process; an in-process Map collapses that to 1 provider call per (geo,geo,bucket) for the process lifetime. This is the ~$100→<$10 driver and is already deployed.
- **KNOWN LIMIT (not a blocker)**: an in-process Map resets on deploy/restart, so the first tick after a restart recomputes. Acceptable because restarts are infrequent vs the per-minute tick storm. A durable `lm_route_cache` Supabase table (columns `(uid, from_geo, to_geo, time_bucket, provider, duration_secs, geometry, computed_at, ttl)` + the migration that was applied this session) exists as an OPTIONAL future upgrade if cross-restart persistence is ever needed; it is NOT wired as the store today, and wiring it is out of scope for this iteration.
- **IN**: route request (from_geo, to_geo, time-bucket). **OUT**: cached value within TTL, else compute-once + store in the Map.
- **INVARIANT**: within one process lifetime, for a given (from_geo, to_geo, coarse-time-bucket) external providers are called ≤1×; a moved event (start changed → new bucket) recomputes; entries older than the 10-min TTL recompute.
