# Spec verdict — round 1

## Overall: FAIL

## Per-dimension

- **Spec Fidelity: FAIL** — `spec/spec.md:8` claims "split into 6 independent failure modes", but the In-scope table enumerates only 5 distinct *failure modes* (C1 EXIF, C2 consec-anchor, C3 cleanup-destroys-edits, C4 WARN-treated-as-success, C5 backspace-fail/✕-overlay-needed) plus 2 documentation-only entries (C6, C7) that are NOT failure modes by any reasonable reading. The count is wrong, OR a 6th failure mode is missing. From the actual retro context, the most likely missing FM is "duplicate-image (cover image and first body image are the same file → got pasted twice)" — the very thing Dais had to manually delete, called out in `spec.md:5-7` ("manually delete 2 duplicate images before publishing"). No C item closes that mode; cover-vs-body dedup is absent from the In-scope table. Spec fails to map the retro symptoms 1-to-1 to fixes.

- **Edge Cases: FAIL** — The spec hard-codes "EXIF orientation = 6" (`spec.md:15`, `spec.md:39`) but EXIF orientations 1–8 exist; tags 3 (180°) and 8 (270° CCW) are equally common from rotated phone shots, and mirrored variants (2/4/5/7) appear from front-camera selfies. The invariant table tests only tag-6 → orientation-tag-None; tags 3/8 are silently unverified. Other misses: (a) `parse_markdown.after_text` is truncated to 80 chars (`parse_markdown.py:178, 204`) so two images whose source paragraphs differ only past the 80-char window will be mis-flagged as "same anchor" (false positive) OR mis-cleared (false negative). (b) Three-or-more consecutive `![…](…)` images: spec only describes pairs (`spec.md:16` "shares the same after_text"); the JSON shape `{block_index, conflicts_with}` is pairwise — a triplet collapses to N-1 pair entries with no transitive grouping. (c) Whitespace-only `after_text` (e.g. image follows an H2 whose text is empty after stripping) — what gets warned? Spec is silent. (d) `--no-cleanup-duplicates` combined with a brand-new title creates orphan duplicate prior drafts forever; spec doesn't say "no-op safely" or "always log how many were skipped". (e) Cover-image PNG path in `copy_to_clipboard.py:76-78` bypasses the PIL pipeline entirely — a phone PNG screenshot with EXIF orientation would be unrotated even after C1, because the early-return PNG branch never opens with PIL.

- **Impl Correctness: FAIL** — C4 (`spec.md:18`) says "delete the wrongly-placed image via the ✕ overlay" but never specifies how the ✕-overlay coordinates are computed. The existing `insert_content_image` retry path (`publish_md_to_x.py:482-563`) does NOT compute or click any ✕ overlay; it just re-anchors and re-pastes. Implementing C4 as-written requires a new helper (locate the newest `<img>`, compute its bounding rect, derive the ✕ button position) that is unspecified, untyped, and shared with C5 (`replace_image_in_draft.py`) — but the spec doesn't extract it into a named contract, so two divergent implementations are likely. Verify-arch `grep -nE "POST-COND WARN.*RETRY|wrong block.*retry" publish_md_to_x.py` (`verify-arch.md:16`) passes on a mere comment string and proves nothing about the actual ✕-click. C3 conflict: `publish_md_to_x.py:619` already gates BOTH cleanups under `--no-cleanup-empties`; spec adds a second flag `--no-cleanup-duplicates` but doesn't define interaction (independent? supersede? what does `--no-cleanup-empties` alone now do — still cleans duplicates?). C5 `--index N --anchor "text"` has overdetermined args: if both are supplied and disagree (image at index N is NOT after `text`), behavior is undefined. C1: `ImageOps.exif_transpose` requires PIL ≥ 6.0 — pinning unstated (`spec.md:52` says "no new deps" but doesn't pin version). Also C1 will silently destroy the *color profile* (ICC) on JPGs because the TIFF re-save (`copy_to_clipboard.py:81-83`) drops ICC unless `icc_profile=img.info.get('icc_profile')` is passed — spec mandates EXIF strip but doesn't say "preserve ICC".

- **Structural Integrity: FAIL** — `verify-arch.md:49` explicitly states the WARN→retry path is "source review only, no live publish". This violates HARD 0.31 (no patch-only completion) for the single highest-risk change in the bundle — the retry path is the fix that prevents a future Dais-loses-work incident, and the spec ships it without ever firing it. The spec must add an explicit hand-off to the main agent: "Phase-2 main-agent live-verify: build a 3-image fixture article that deliberately triggers the WARN branch (same after_text on images 2 + 3) and confirm the retry deletes image 3 and re-anchors". Otherwise "Done" by these criteria leaves the retry untested in reality. Secondary: `spec.md:23-31` "Out-of-scope" mentions Dais's live article URL but doesn't require a runtime guard (e.g., refuse to operate if URL is the published one) — relies on human discipline, mild HARD 0.33 smell. Tertiary: C5 creates a new entry-point that handles destructive edits on an existing draft, yet spec has no "abort if more than 1 image at index N candidate" or "abort if `--src` and on-page image have identical bytes" safety — destructive primitive without invariants.

- **Verification Readiness: FAIL** — E1 (`verify-arch.md:25`) requires `copy_to_clipboard.py` to run in "dry-mode that writes the to-be-clipboarded bytes to a file". That mode does not exist in `copy_to_clipboard.py` today (see entire file: only `image` and `html` subcommands, both push to macOS pasteboard, no `--dry-write`). The spec does not list adding `--dry-write <PATH>` as a sub-task of C1. As written, E1 is unrunnable from disk → adversary cannot verify the most-important invariant. E4 (`verify-arch.md:28`) only checks `--help`; it does NOT test the spec's claim that "running it with a fake draft URL fails gracefully (no destruction)" (`spec.md:44`) — there is no assertion, no fixture, no expected exit code for the destructive-safety claim. E5 (`verify-arch.md:29`) asks "previous lessons remain" but provides no committed `wc -l`/digest baseline file; at adversary time the "before" snapshot does not exist on disk, so the test cannot run deterministically. Fixture location `.vcsdd/features/.../tests/` (`verify-arch.md:23`) is referenced but the directory and JPG-with-EXIF-tag-6 builder script are not enumerated in the spec — adversary cannot run any E2E without inventing them. E2's stderr regex `/WARN.*consecutive/i` is loose enough to pass on any unrelated WARN line that happens to contain the word "consecutive".

## Top-3 must-fix (in order)

1. **Enumerate the 6 failure modes verbatim**, then map each to a C-item. Add the missing failure mode FM-6 "cover-image is also first body-image → pasted twice in body" (the literal duplicates Dais deleted in `spec.md:5-7`), and add the corresponding C-item (e.g., `C0: in publish_md_to_x.py, skip any content_image whose absolute path == cover_image's absolute path; emit log "cover-dup-skip"`). Without this, the spec's central claim ("each must be closed so the NEXT article ships clean") is unsubstantiated and the very symptom that triggered this iteration (manual duplicate deletion) is left unfixed.

2. **Make E1 actually runnable**: add a sub-task to C1 that introduces `python3 copy_to_clipboard.py image <path> --dry-write <out.bin>` which writes the post-EXIF-transpose, EXIF-stripped image bytes to disk and skips the pasteboard. Then E1 can `Image.open(out.bin)` and assert orientation tag is None + dimensions transposed. Also expand C1 to cover the PNG branch in `copy_to_clipboard.py:76-78` (it currently bypasses PIL → no EXIF rotation possible for PNG). And expand E1 to exercise EXIF orientations 3 and 8 in addition to 6.

3. **Specify and share the ✕-overlay deletion primitive** used by both C4 (retry) and C5 (replace). Define a function with a stable name/signature (e.g., `delete_image_block(page, img_index: int) -> bool` in a shared helper module), specify (a) how it locates the target `<img>` (selector + index), (b) how it computes ✕-overlay coords (bounding-rect of the figure + fixed offset, or hovering + querying the close button selector), (c) post-condition: img count decreased by exactly 1, no other block mutated. Then C4 and C5 both call it. Replace `verify-arch.md:16` grep with `grep -nE "def delete_image_block\(" <shared.py>` so the verify is load-bearing on the actual behavior, not a free-form comment string. Also add a Phase-2 main-agent live-fire fixture article (≥3 images, 2 sharing the same after_text) that exercises the WARN→retry branch in a real CDP session — close the HARD 0.31 gap that `verify-arch.md:49` currently leaves open.

## Notes

- `parse_markdown.py:178, 204` truncates `after_text` to 80 chars — the C2 collision detector inherits this truncation. The spec should explicitly say "consecutive_anchor_collision is computed on the SAME truncated 80-char after_text used by downstream insert logic" (so detector matches reality) and document that fix-by-extending-after_text is OUT of scope (or move it IN).
- C1 should also pass `icc_profile=img.info.get('icc_profile')` and `format='TIFF'` quality params explicitly, else stripping EXIF unintentionally strips color profile — would mute the very phone photos C1 is fixing.
- C3 + the existing `--no-cleanup-empties` flag interaction is undefined. Suggest a single `--cleanup-mode {all,empties-only,duplicates-only,none}` rather than two booleans whose AND/OR semantics are ambiguous.
- C5's `--anchor "text"` is redundant with `--index N`. Either drop `--anchor` or define it as a *post-condition assertion* (the image AT index N must follow `text`; otherwise abort) — make the redundancy a safety check, not an ambiguity.
- `spec.md:30-31` "Do NOT modify Dais's now-LIVE article" is a human discipline note; add a runtime guard in `replace_image_in_draft.py` that refuses to operate on URLs containing `2070894941786796033` (or, better, any URL matching the live-article shape vs draft shape) so the prohibition is mechanically enforced.
- L1 grep `--no-cleanup-duplicates` ≥1 + `no_cleanup_duplicates` ≥2 (`verify-arch.md:14-15`) passes trivially with one comment + one CLI declaration + one usage — does not prove the gate is in the right place. Strengthen to `grep -nE "if not args\.no_cleanup_duplicates:\s*$" publish_md_to_x.py` → ≥1 hit.
- E5 needs a committed "before" digest (e.g., `tests/skill-md-baseline.sha256`) so the append-only assertion is deterministic post-edit.
- The spec does not list the new file `scripts/replace_image_in_draft.py` under a fixed path (`spec.md:19` says NEW but no path). State the absolute path so the grep at `verify-arch.md:17` knows where to look.
