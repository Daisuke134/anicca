## Item 2 — REQ-016 (HMAC mitigation): honesty and correctness

**(a) Secret never reaches the loop under test, forced by a PROP — CONFIRMED.**
`behavioral-spec.md:578-582` (EARS text): secret generated by CSPRNG inside the wrapper
process, passed to `public_artifact_snapshot.py` "through a channel not observable to the loop
under test (never a CLI argument, never an env var exported into the loop's own environment,
never written to the trail directory)." `behavioral-spec.md:606-607` (PROP-051, required): "the
secret never appears in the wrapper's argv, in any env var visible to the spawned loop/verifier,
or anywhere under the artifact-trail directory (mechanical check)." This is forced, not aspirational.
(Minor, non-blocking, noted for completeness only: the spec never names the actual channel used
to hand the secret to the Python subprocess — e.g. a dedicated env var scoped only to that
subprocess's own exec, or stdin — leaving the concrete mechanism to the Builder. Not blocking:
PROP-051 mechanically forces the property regardless of which mechanism is chosen.)

**(b) Unsigned/mis-signed row fails to count as a valid capture, fail-closed — CONFIRMED.**
`behavioral-spec.md:583-586`: "`enforceVerdict` SHALL recompute the HMAC for every cited row and
treat any row that is unsigned, mis-signed, or signed with a different pass's secret as **not a
valid capture** → the verdict cannot reach PASS on it." `behavioral-spec.md:603-605` (PROP-049,
required): unsigned row → never a valid capture. `behavioral-spec.md:604-606` (PROP-050,
required): row signed under a different secret → never a valid capture. Forced correctly.

**(c) Does the signing layer create a NEW laundering channel (FAIL → `CANNOT_VERIFY`)? YES —
BLOCKING, and this is the review's central finding.**

`behavioral-spec.md:608-610` (PROP-052) tests exactly the narrow case the task brief names: "a
valid, correctly-signed row that CONTRADICTS the claim still yields `FAIL`." That specific case
is genuinely forced and I found no way to defeat it as stated.

But PROP-052 only covers a row that **remains** correctly signed. It does not cover — and no
PROP anywhere covers — a row that **was** correctly signed by the real capture tool (and, at
the moment of writing, genuinely contradicted the claim, e.g. a real `404`), and is then
**tampered with, after the fact, by the loop under test** (same-uid write access to
`artifacts.jsonl` — nothing in REQ-016 or the NFR section restricts write permissions on this
file to exclude the loop under test; REQ-016 only protects the secret used to *produce* a valid
signature, not the file's mutability once written). Tampering with the row's bytes without
knowing the secret makes the recomputed HMAC mismatch — i.e. it becomes exactly a "mis-signed"
row under REQ-016's own definition (`behavioral-spec.md:583-584`, "treat any row that is
unsigned, mis-signed... as **not a valid capture**"). Per REQ-016's own fallback rule
(`behavioral-spec.md:585`, "fail-closed: `CANNOT_VERIFY` if no valid capture remains"), if the
tampered row was the only citation, the outcome is `CANNOT_VERIFY` — **not** `FAIL`.

This is a materially different, and materially *worse*, situation than the pre-REQ-016 state,
which the spec's own taxonomy already handled correctly: `behavioral-spec.md:207-225` (REQ-004's
table, unmodified by this iteration and never cross-referenced from REQ-016) has exactly two
citation-resolution outcomes for a "row that doesn't check out": (i) `no_citation` — zero
citations attempted at all → `CANNOT_VERIFY` (correctly INCONCLUSIVE: nothing was ever
attempted); (ii) `no_matching_row` — a citation resolves to **no real row at all** (e.g. the row
was deleted) → **CONTRADICTION → `FAIL`** (correctly treated as dishonest: a citation to
evidence that provably does not exist). Simple deletion of a genuine row is therefore *already*
closed by the existing table — it produces `FAIL`, exactly as it should.

REQ-016 introduces a **third, new intermediate state** — a row that is structurally present
(resolves, has the right `passId`/`seq`/shape) but fails signature verification — and this state
is never entered into REQ-004's table at all. REQ-016's own prose (not REQ-004's table) is the
only place this state is classified, and it classifies it into the "not a valid capture" bucket,
which per line 585 falls through to `CANNOT_VERIFY`. This directly contradicts the spec's own
stated invariant at `behavioral-spec.md:560-562`: "The CONTRADICTION-vs-INCONCLUSIVE taxonomy
(REQ-004) is itself a fixed, deterministic lookup table — which violation TYPE maps to which
OUTCOME is decided once, in this spec, never by the LLM at runtime and never by a heuristic
guess about severity" — REQ-016 adds a new violation type entirely outside that table.

Concretely, and worse: this attack requires **no secret at all** — only ordinary same-uid file
write access, a capability the spec already grants the loop under test everywhere else (FIND-S,
row 12(b)). `behavioral-spec.md:592-596` (REQ-016's own honesty disclosure) names the residual
same-uid risk as "a determined same-uid adversary can still attack the secret" — but the attack
described here never touches the secret; it corrupts a signature it can't reproduce, which is
sufficient on its own to launder `FAIL` into `CANNOT_VERIFY`. The disclosure text therefore
**understates** REQ-016's actual residual risk, and no `required: true` PROP forbids it.

**Concrete fix required**: `enforceVerdict`/`validateArtifactProvenance`'s taxonomy (REQ-004)
must be amended to add a THIRD citation-resolution outcome, distinct from `no_citation` and
`no_matching_row`: a citation that resolves to a row which is structurally present (right
`passId`/`seq`) but whose `rowHmac` does not verify against a recomputation — classify this as
its own **CONTRADICTION** (e.g. `row_tampered`), mapping to `FAIL`, not folded into "not a valid
capture → `CANNOT_VERIFY`". Only a citation to a `passId`/`seq` with **zero** rows present at
all should ever reach `CANNOT_VERIFY`/`no_citation`; any row that exists but fails signature
verification is itself positive evidence of tampering and must be treated with the same severity
as `no_matching_row`. This closes the gap without weakening PROP-049/050/051/052, and needs its
own required PROP (e.g. "a row present at the cited `passId`/`seq` with an invalid `rowHmac` →
`FAIL`/`row_tampered`, not `CANNOT_VERIFY`, even when it is the only citation").

**(d) Does the spec overstate what HMAC buys / claim row 12 closed? NO — CONFIRMED honest, not
blocking.** `behavioral-spec.md:83` (closure row 12): "**OPEN — disclosed architectural limit,
NOT closable by spec text.** MITIGATED (not closed) by REQ-016's HMAC row signing..."
`behavioral-spec.md:592-596`: "it is a bar, not a wall... **A verifier cannot be made
cryptographically sound against a loop that shares its trust domain.** This spec therefore
declares row 12 OPEN and records the only real fix as future architectural work..." No language
anywhere in either document claims row 12 is closed. (This finding does not change that
assessment — REQ-016's own disclosure already says the mitigation is incomplete; item (c) shows
the incompleteness is larger, and differently shaped, than the disclosure names.)

## Item 3 — Regression: can a lying loop weaponize `CANNOT_VERIFY` after this iteration's changes?

**Concrete answer**: yes, via the exact mechanism found in item 2(c) above, which is the
sharpest, most directly actionable instance of this weaponization found across this and the
prior review. Restated as the attack a lying loop would actually run: post a fabricated claim;
if the real capture tool's genuine row happens to record a real contradiction (e.g. a real
`404`, or a fixed-surface/fingerprint mismatch), the loop — using only its already-granted
same-uid Bash capability, no secret required — overwrites or appends garbage to that row's bytes
in `artifacts.jsonl` before/while `enforceVerdict` reads it. The row's HMAC no longer verifies →
"not a valid capture" (`behavioral-spec.md:583-585`) → `CANNOT_VERIFY`, not the `FAIL` the
genuine, captured contradiction warranted.

Checking the four sub-questions the brief specifies, against the resulting `CANNOT_VERIFY`:
- **(i) Never counts as success** — TRUE, unaffected by this gap. `behavioral-spec.md:351-353`
  (REQ-010): a `CANNOT_VERIFY` verdict SHALL NEVER be treated as sufficient to satisfy a `PASS`
  claim; REQ-004/008/009's fail-closed recording/convergence rules apply identically to it.
- **(ii) Never reported to the owner as a verified post** — TRUE but weaker than it sounds.
  `behavioral-spec.md:353-356` and `376-381` (REQ-010/REQ-011) both state, in **negative** form
  only, that `CANNOT_VERIFY` must never be reported "AS verified." Neither requirement states,
  in **positive** form, that `CANNOT_VERIFY` outcomes MUST actually be surfaced anywhere in an
  owner-facing report/summary. `behavioral-spec.md:354` cites "REQ-011 requires it be surfaced
  explicitly AS `CANNOT_VERIFY`" — but REQ-011's own text (`behavioral-spec.md:368-399`) contains
  no such positive surfacing requirement anywhere; it only forbids the false-positive framing.
  This citation is not actually backed by the requirement it cites.
- **(iii) Blocks convergence** — TRUE, unaffected. `behavioral-spec.md:334-336` (REQ-009):
  `CANNOT_VERIFY` blocks convergence identically to genuine `FAIL` via REQ-008's schema mapping.
- **(iv) Visible as a recurring anomaly, itself an alarm** — PARTIALLY TRUE, and this is the gap.
  `behavioral-spec.md:357-361` (REQ-010 edge case) is genuinely required: the human-review queue
  is append-only, "THE SYSTEM SHALL NOT deduplicate or suppress repeated appends." So a
  persistent `CANNOT_VERIFY` streak IS durably recorded and never hidden or collapsed. But
  durable-and-unsuppressed is not the same as **alarmed**: nothing in either document requires
  that N consecutive (or any threshold of) `CANNOT_VERIFY` results actively escalate — to a
  human, to a monitoring loop, or into the owner-facing report — the way a genuine `FAIL`
  actively triggers `self-fix.sh` (a positive, forcing action). A loop whose evidence is
  permanently `CANNOT_VERIFY` (whether via the tampering vector above, the pre-Phase-2a
  diagnosability gap, or the FIND-S race) produces rows in a file that nothing in this spec
  requires anyone or anything to read. I grepped both spec files for `owner|daily summary|
  consecutive|streak|escalat` and found no requirement or PROP establishing an active-alert or
  N-consecutive-escalation rule anywhere (`verification-architecture.md:155` even names this
  class of gap explicitly as an accepted, out-of-scope disclosure: "Whether a `CANNOT_VERIFY`
  outcome will, in practice, ever actually get resolved... this feature specifies the MECHANISM...
  but does not, and cannot from a Phase-1c spec, guarantee operational follow-through").

**This is BLOCKING per the brief's own stated bar**: a permanently-`CANNOT_VERIFY` loop can, in
fact, look silently healthy to its owner — its daily summary (if REQ-010's parenthetical example
is implemented literally) has no requirement to mention `CANNOT_VERIFY` counts at all, and no
escalation fires no matter how many consecutive `CANNOT_VERIFY` results accumulate. The concrete
fix the brief asks for: add a required rule (its own REQ or acceptance criterion under REQ-010/
REQ-011, with a forcing PROP) that (a) the owner-facing report/summary MUST positively include a
`CANNOT_VERIFY` count/flag for the reporting period (not merely "never call it verified"), and
(b) N consecutive `CANNOT_VERIFY` results for the same loop (a small, spec-fixed N, e.g. 3)
escalate through the SAME channel as a genuine `FAIL` (i.e. also invoke a review-triggering
action, not `self-fix.sh` specifically since there is no code bug, but something that is not
"append a line to a file nobody is required to read").

## Findings (this delta)

- **FIND-U (BLOCKING, new this iteration)** — REQ-016's "unsigned/mis-signed → not a valid
  capture → `CANNOT_VERIFY` if none remain" fallback (`behavioral-spec.md:583-586`) is never
  distinguished from a row that WAS genuinely signed and contradicted the claim, then was
  tampered with after the fact by the loop under test using ordinary same-uid file-write access
  (no secret needed). REQ-004's taxonomy (`behavioral-spec.md:207-225`), the spec's own declared
  single source of truth for violation classification (`behavioral-spec.md:560-562`), has no
  entry for "row structurally present, signature invalid" — only `no_citation` (nothing cited,
  → `CANNOT_VERIFY`, correct) and `no_matching_row` (row provably absent, → `FAIL`, correct).
  PROP-052 only forces the narrower case where the row REMAINS correctly signed. No PROP
  prevents laundering a captured contradiction into `CANNOT_VERIFY` by corrupting its signature
  after the fact. REQ-016's own disclosure (`behavioral-spec.md:592-596`) names the residual risk
  as "attack the secret," which understates this zero-secret-required vector. `routeToPhase`: 1b.
  Fix: add a `row_tampered` CONTRADICTION classification (→ `FAIL`) for any citation that
  resolves to a structurally-present row whose `rowHmac` fails recomputation, with its own
  required PROP, distinct from and never folded into the `CANNOT_VERIFY` fallback.
- **FIND-V (BLOCKING, new this iteration)** — No requirement or PROP anywhere establishes an
  active escalation for a persistent `CANNOT_VERIFY` streak, and REQ-010's claim that "REQ-011
  requires [`CANNOT_VERIFY`] be surfaced explicitly" (`behavioral-spec.md:354`) is not actually
  backed by REQ-011's text (`behavioral-spec.md:368-399`), which only forbids the false-"verified"
  framing, never mandates positive surfacing. `verification-architecture.md:154-160` explicitly
  accepts "whether a `CANNOT_VERIFY` outcome will ever actually get resolved" as out of scope.
  Combined with FIND-U (and, independently, with review 07's still-open FIND-S), a loop can be
  permanently `CANNOT_VERIFY` and remain silently healthy-looking to its owner: durably logged,
  never deduplicated, but never alarmed on and never required to appear in any owner-facing
  summary. `routeToPhase`: 1b. Fix: require (a) the owner-facing report to positively include a
  `CANNOT_VERIFY` count for the period, and (b) N consecutive `CANNOT_VERIFY` results for the
  same loop to trigger an active, spec-named escalation action, not merely a durable log append.

No other new blocking or major findings within the granted scope. Item 1 (FIND-T) is genuinely,
fully fixed. Items 2(a)/2(b)/2(d) are genuinely, fully honest and correctly forced. FIND-U and
FIND-V are both narrow, mechanical gaps in the REQ-016 addition and its interaction with the
existing three-outcome design — not a rejection of the HMAC-signing direction itself, which
remains real progress against forgery-from-scratch (PROP-049/050 are genuinely forcing).
