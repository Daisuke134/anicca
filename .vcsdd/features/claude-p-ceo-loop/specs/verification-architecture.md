# Verification Architecture — claude-p-ceo-loop (Phase 1b, mode: lean)

## Purity boundary map

このfeatureが新設する全モジュールについて、「純関数として単体テスト可能な部分」と「副作用境界
（実ファイル読み書き・実mail送信・実launchd/日時判定）」を分離する。既存コードが既に実践している
分離パターン（`cadence.py`の`cadence_met`/`streak`、`guardrails.py`の4関数、`record-earn.mjs`の
`writeCursorAtomic`、Mahoraga `save_state`/`load_state`のtmp+atomic-rename、agent-os
`budgets.py`のread-aggregate関数群）をそのまま再利用し、新しい分離方式を発明しない。

**Cross-cutting invariants（behavioral-spec.md参照、Phase 1c iteration-4/5 adversary指摘B7/B8/B9/
B10/B11の構造修正）**: INV-CEO-1（`_usd`/`_usdc`型パラメータ・フィールドは全て`realized_profit_usd()`
経由、B10でREQ-CEO-060の`weekly_realized_profit_usd`を列挙に追加）と INV-CEO-2（副作用REQは全て
CEO WEEKLY pass=REQ-CEO-058の①〜⑫に配置——ただしB11で明示した2つの正当な例外〔REQ-CEO-020は
PER-LOOP-PASS、REQ-CEO-070はシーケンスの呼び出し元〕を除く、`loop-registry.json`への実I/Oは
1 passにつき1回のみ〔REQ-CEO-044〕）は、個別REQの表に散らばる検証項目ではなく、下表の複数行・
複数PROPを横断して検証される不変条件である。PROP-CEO-013/015/PROP-CEO-023がINV-CEO-1/2それぞれの
中心的な反証テストを担う。**B9修正（道A、team-lead指示2026-07-08）**: iteration-4版は複数ステップ
（③-c/⑥/⑧-c）が共有可変dict `registry_updates` へ異なる粒度で逐次queueする設計だったが、この
「アキュムレータへの逐次queue」という仕組み自体が内部マージ順序未定義という新たな欠陥クラス（B9）を
生んだため廃止し、各ステップが完全にローカルな戻り値（`budget_snapshot_by_loop`/`rollback_restore`/
`allocation_decisions`）だけを返し、それらをステップ⑨の`build_next_registry()`（REQ-CEO-044）が
名前付き引数として一度だけ受け取り組み立てる設計に置き換えた。`merge_loop_registry_updates`と
`merge_allocation`は独立した公開関数としては廃止され、`build_next_registry`に統合された。

  `~/.claude/CLAUDE.md`モデル分業表準拠）によるPASS/FAIL判定。
