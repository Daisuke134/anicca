## Observed Boundaries

Verified by direct control-flow reading of the current code (paths as of this Phase 5 pass; line numbers may drift by a few lines from future commits but the structure below was re-derived from the actual files, not copied from the spec).

1. **`isLockStale` — CONFIRMED PURE.** `skills/economy/gig/lib/lock.mjs`: `export function isLockStale(nowMs, mtimeMs, staleMs) { return (nowMs - mtimeMs) > staleMs; }` — a single arithmetic comparison, no `fs`/`crypto`/`Date.now()`/randomness inside the function body itself (the caller supplies `nowMs`). `acquire()` calls `tryCreateLockFile()` then, on failure, `reclaimStaleLock(file, staleMs)`, which calls `isLockStale(Date.now(), stat.mtimeMs, staleMs)` by name — no inline `Date.now() - stat.mtimeMs > staleMs` comparison exists anywhere else in the file. Matches the declared boundary exactly, including the binding "independently exported, called by name" acceptance criterion.
2. **`acquire`/`release`/`touch`/`withGigLock`/`tryCreateLockFile`/`reclaimStaleLock` — CONFIRMED EFFECTFUL.** All perform real `fs.mkdir`/`fs.open(file,"wx")`/`fs.stat`/`fs.rename`/`fs.unlink`/`fs.utimes`, and `withGigLock` runs a real `setInterval` heartbeat. None of these are exported as "pure" anywhere in the spec, and none behave as pure in the code. Matches.
3. **`store.mjs` — untouched, still pure.** Not modified by this increment's diff (confirmed via `git log -p` scope of this sprint's commits touching only `lib/lock.mjs`, `gig.mjs`, `catalog-gate.mjs`, `index.mjs`, `registry.json`, and their `__tests__`). Matches.
4. **`gig.mjs::applyAndSave`/`gigPost`/`gigTake`/`gigDeliver`/`gigVerifyAndPay` — CONFIRMED EFFECTFUL ORCHESTRATION.** `applyAndSave` re-reads `loadState(statePath)` freshly inside the `withGigLock(BOARD_LOCK_KEY, ...)` critical section on every call (never a stale snapshot); the bounded retry loop (`BOARD_LOCK_RETRY_ATTEMPTS`/`_DELAY_MS`) wraps only the shared `"_board"` lock, never the per-gigId lock. `gigVerifyAndPay` performs the real network settle (`pay()`) INSIDE the per-gigId `withGigLock`, before calling `applyAndSave`. Matches the declared "properties of THIS module's call ordering" characterization exactly.
5. **`catalog-gate.mjs::filterCatalog` — CONFIRMED PURE.** Full read of the function body: takes `{ balanceUsdc, allSlotNames, riskTagOf, alwaysAvailableOf, hasOpenRiskPositionOf, reserveThresholdUsdc }`, does only array/boolean arithmetic (`Array.isArray`, `.slice()`, `.filter()`, three boolean-returning callback invocations), no `fs`/`network`/`Date`/`Math.random` anywhere in the module. `effectiveThreshold`/`isBelowThreshold` (its two private helpers) are likewise pure. The 11 required Tier-1 obligations that name this function (PROP-201a/b/c/d/e/f, PROP-202a) were additionally property-tested in this Phase 5 pass (`verification/proof-harnesses/catalog-gate.proof.mjs`) across thousands of randomized inputs with zero I/O performed — reinforces rather than contradicts the declared boundary.
6. **`catalog-gate.mjs::hasOpenRiskPositionOfYield` — CONFIRMED PURE / NO NEW I/O.** `const ledger = Array.isArray(recentLedger) ? recentLedger : []; ... ledger.slice().reverse().find(...)` — operates only on the array argument passed in; no `fs`/`fetch`/network call anywhere in the function body. This Phase 5 pass additionally property-tested it (`catalog-gate.proof.mjs`, PROP-201h) against an independent oracle re-implementation across ~3000 randomized ledger shapes (including non-array/null/undefined malformed inputs), all passing with zero I/O performed during the test run. Matches the declared "no new I/O" claim precisely.
7. **`catalog-gate.mjs::hasOpenRiskPositionOfHlTrade` — CONFIRMED EFFECTFUL, LAZY, FAIL-OPEN.** `async function hasOpenRiskPositionOfHlTrade({ balanceUsdc, reserveThresholdUsdc, queryFn })`: computes `effectiveThreshold`, returns `false` immediately (no `queryFn()` call) when `!isBelowThreshold(...)`; otherwise calls `await queryFn()` inside a `try`, and the `catch` block explicitly `return true;` (fail-open, with an inline comment confirming this is deliberate — the only fail-open branch in the whole gate). Matches the declared EFFECTFUL/lazy/fail-open characterization exactly; this is genuinely new effectful-shell surface, correctly NOT classified as pure.
8. **`index.mjs` wiring — CONFIRMED EFFECTFUL SHELL, boundary correctly drawn.** Read end-to-end (current line numbers noted; drift a few lines from the spec's cited "~L100-118"/"~L190-196" is cosmetic, not a scope violation):
   - Registry read (`fs.readFile(registryPath, ...)`, ~L119) happens once at module load, populating `activeSkillSlots`/`skillCatalog`/`riskTagBySlot`/`alwaysAvailableBySlot` — wrapped in `try/catch` with a fail-safe fallback to `['earn']` on read failure (an additional safety property beyond what the spec required, not a boundary violation).
   - `riskTagOf`/`alwaysAvailableOf` (~L138-143) are plain object lookups into the already-loaded `riskTagBySlot`/`alwaysAvailableBySlot` maps — no I/O of their own, correctly usable as pure-looking callbacks passed into the pure `filterCatalog`.
   - `fetchUsdcBalance` (~L239) is a real RPC call, wrapped in `try/catch` (failure keeps the prior tier) — effectful, as declared.
   - `hasOpenRiskPositionOf('yield')` (~L299-304, `openPositionYield = hasOpenRiskPositionOfYield(recentLedger)`) reuses the SAME `recentLedger` array already used to compute `positionsSummary` two lines above it — genuinely no new I/O, confirmed by reading the surrounding code, not merely trusting the comment.

   - No new steering/preference text is introduced by this increment's own diff in `index.mjs`; `eligibleSkillSlots` is passed straight into `assembleContext` as `activeSkillSlots` with no added text (confirms PROP-203b/Gate item (4) for this increment's own new code).
9. **`registry.json` — CONFIRMED DATA, not code.** Parsed as static JSON; `risk`/`alwaysAvailable` fields on each of the 17 `status:"live"` slots are plain string/boolean literals, never computed. Matches.

## Summary

**No purity/effect-boundary drift detected.** Every declared boundary in `specs/verification-architecture.md`'s Purity Boundary Map was independently re-derived from the current implementation (not merely re-read from the spec's own claims) and matches exactly:
- `isLockStale` is genuinely pure and genuinely the sole staleness-decision path (no inline duplicate comparison survives anywhere in `lock.mjs`).
- `filterCatalog` and `hasOpenRiskPositionOfYield` are genuinely pure, zero-I/O, and this Phase 5 pass adds fast-check property-based coverage (thousands of random cases each) that further stress-tests this claim beyond the Phase 2 handwritten fixtures — see `verification/proof-harnesses/`.
- `hasOpenRiskPositionOfHlTrade` and all `lock.mjs`/`gig.mjs`/`index.mjs` orchestration functions are genuinely effectful, and the two lazy/fail-open properties (invoked only below threshold; fails OPEN, not closed, on query failure) hold on direct code reading, consistent with the Phase 3 adversary's independently-tested confirmation of the same (CRIT-006 in `reviews/impl/sprint-1/output/verdict.json`).
- No hidden side effects were found inside any function classified as pure (no `fs`, network, `Date.now()`/`Math.random()`, or module-level mutable state read/written by `filterCatalog`, `isLockStale`, or `hasOpenRiskPositionOfYield`).
- One **process observation, not a code drift**: `specs/verification-architecture.md` itself labels PROP-101d as Tier 1 ("does not depend on isLockStale... remains Tier 1"), but the only exported surface that can observe two-different-keys independence is `withGigLock()`, which is effectful (real `fs.mkdir`/`fs.open`/`fs.stat`). The existing Phase 2 handwritten test for PROP-101d already exercises this through real fs (`skills/economy/gig/__tests__/lock.test.mjs`), and this Phase 5's new fast-check harness for PROP-101d (`verification/proof-harnesses/lock-key-independence.proof.mjs`) does the same, honestly labeled as Tier 2 in its own file header rather than silently claiming Tier 1 purity it does not have. This is a documentation/tier-labeling nit in the spec, not an implementation purity violation — `lockPaths()`/`acquire()` remain correctly unexported internals, and no product code needed to change. Recommend correcting the Tier column for PROP-101d to "1/2" (matching the pattern already used for PROP-101c/103a) in a future spec revision; not blocking for this Phase 5 pass since the property itself is proved either way.
- **No follow-up required before Phase 6** on purity grounds. (See `security-report.md` for a separate, non-purity-related path-traversal finding surfaced during this Phase 5's security sweep — that finding is about input validation, not about the core/shell purity split, and does not change any of the above boundary classifications.)
