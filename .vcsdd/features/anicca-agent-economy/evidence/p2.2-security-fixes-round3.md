# P2.2 security fixes (round 3) — 2 residual concurrency gaps, not fund-theft but real data-loss

**日付**: 2026-07-07 · **builder**: VCSDD builder (same session, continued from
p2.2-security-fixes.md) · **worktree**: `~/anicca/.worktrees/agent-economy`（branch
`feature/agent-economy`、local commit, not pushed）

## Findings (from the team lead's second adversary pass)

A fresh adversary confirmed all 3 round-2 fund-drain findings CLOSED, then found 2 residual
concurrency gaps that would bite once automaton + Franklin (separate concurrent launchd loops) both
use this board:

1. **GAP 1 (stale-lock steal)**: `lib/lock.mjs`'s `STALE_MS=30000` let a second caller STEAL a lock
   after 30s and run `fn()`, but a legit-slow (not crashed) settle can exceed 30s under congestion
   (adversary measured a real `insufficient_funds` retry sequence at 16.79s, plus network/confirmation
   on top) — reopening the round-2 double-pay race.
2. **GAP 2 (cross-gig shared-state clobber)**: the per-gigId lock never protected the SHARED
   `state/gigs.json` file — `persist.mjs` is a full-file overwrite with no version check, so a slow
   operation on gig X would compute its eventual save from a state snapshot captured BEFORE its slow
   network step; that late save would silently revert a concurrent `gig_take` on an unrelated gig Y
   back to `'open'` — the legit taker's assignment would vanish from the persisted board even though
   `gig_take` had already returned `{ok:true}` to its caller.

## Fixes (all in `~/anicca/skills/economy/gig/`)

| File | Change |
|---|---|
| `lib/lock.mjs` | GAP 1: `withGigLock` now starts a `setInterval` heartbeat (`heartbeatMs`, default 5s) that touches the lock file's mtime for as long as `fn()` is running; only cleared in the `finally` block alongside release. `STALE_MS` raised from 30s to a configurable `staleMs` (default 60s) — with the heartbeat in place, staleness now only ever indicates a genuinely dead (crashed, no heartbeat) holder, never a merely slow one. Both `staleMs`/`heartbeatMs` are injectable via a 4th `options` param (production defaults preserved; tests use tiny values). |
| `gig.mjs` | GAP 2: new `applyAndSave(statePath, mutateFn, lockConfig)` helper — the ONLY place that ever writes to disk. It runs inside a NEW global `"_board"` lock (separate key from the per-gigId/`"_post"` lock), and re-reads the board FRESH from disk immediately before calling `mutateFn(state)` and saving. `gigPost`/`gigTake`/`gigDeliver`/`gigVerifyAndPay` were restructured so their (possibly slow) network step still holds only the per-resource lock (gigId or `"_post"`), while the actual mutation+save is deferred to `applyAndSave`'s brief, always-fresh critical section — preserving throughput across unrelated gigs while guaranteeing no lost update. |
| `__tests__/lock.test.mjs` (NEW) | 3 tests: heartbeat prevents a live holder's lock from being stolen; a genuinely dead holder's lock (no heartbeat, past staleMs) IS reclaimable; unrelated lock keys never contend with each other. |
| `__tests__/gig.test.mjs` | +1 test (`★GAP 2★`): a slow `gig_verify_and_pay` on gig X, racing a concurrent `gig_take` on unrelated gig Y, confirms Y's take survives in the final persisted board. |
