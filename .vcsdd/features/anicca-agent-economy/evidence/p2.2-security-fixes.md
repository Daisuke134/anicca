# P2.2 security fixes (round 2) — adversary drained the escrow live, twice

**日付**: 2026-07-07 · **builder**: VCSDD builder (same session, continued from p2.2-gig-board.md) ·
**worktree**: `~/anicca/.worktrees/agent-economy`（branch `feature/agent-economy`、local commit, not pushed）

## Findings (from the team lead's adversary report)

1. **FINDING 1 (critical, no poster auth)**: `gig_verify_and_pay` checked ZERO caller identity — the
   taker itself took a gig, delivered garbage, and called `verify_and_pay(true)` on itself, draining
   the escrow. Real tx: `0x78111fa62b82d9e94b2f7609cca40592e7cd824991c4a3667cf99b6572e68555` (escrow →
   `0xc7d7dec0be728d930d777aaec5afe114e197d8c1`, an attacker wallet distinct from any test wallet of
   mine).
2. **FINDING 2 (critical, double-pay race)**: no lock around `gigVerifyAndPay`'s
   load→(network wait)→save. Two concurrent `verify_and_pay(true)` calls on one gig BOTH paid; the
   JSON ledger only recorded one (last-write-wins). Real tx:
   `0xd0af29c3c0c119d62f32c48c3e63273db0344fb58fbc68962afd9c03ef59fc08` +
   `0x6573886bc22ac7a39ce9e22db0ed1864a5c32b83227563d3dcd8b794018f7e54` (both escrow →
   `0xb7b195e0302e6b9edb6e083a690754996507a15a`).
3. **FINDING 3 (decorative ERC-8004)**: identity registration worked, but `gigTake`/`gigVerifyAndPay`
   never called `verifyIdentity` — strangers weren't actually protected.
4. **FINDING 4 (test gap)**: all 10 existing tests hit `store.mjs` pure functions; `gig.mjs`
   (where the bugs live) had zero tests.

## Bug found + fixed live DURING this re-proof (same RPC-lag class, different read path)

First attempt at the clean re-run failed the legit `gig_verify_and_pay` on GIG A with
`insufficient_funds` — moments after a real, confirmed-mined `gig_post` funding tx
(`0x9499c4145c553136c882e9052a2b716828e7c1e0308fd7c655f3c24355380c9b`, receipt `status:0x1`, USDC
`Transfer` event decoded: `0xde6caf...` → `0x72fa5624...`, value `0x3e8`=1000). Cross-checked the
escrow's balance via TWO independent public RPC endpoints (`sepolia.base.org` and
`base-sepolia-rpc.publicnode.com`) — both agreed, ruling out a simple client-side stale read; the
actual root cause is the facilitator's OWN internal RPC connection (a separate process) lagging behind
the just-mined block by a few seconds — the same propagation-lag class already documented for
ERC-8004 `ownerOf()` in `lib/identity.mjs`, now observed on the facilitator's balance preflight too.

**Fix**: `lib/escrow.mjs`'s `verifyWithRetry()` retries `/verify` with backoff (3s, 5s, 8s) ONLY when
the rejection reason is exactly `insufficient_funds` — any other rejection reason fails immediately
(no masking of a genuine insufficient-balance error). Confirmed the fix resolves the race: a direct
retry call against the stuck gig succeeded (tx
`0xbc02da0869aa818e9e0de59d928f7b774a9d105b388158e9f6db6e774c5b0462`), then a fully clean re-run from
scratch (table above) hit no further transient failures.

## Gaps / honest scope limits (unchanged from round 1, still true)

- Escrow is still a custody keypair, not a Solidity contract (documented, out of scope for P2.2).
- Bindu `bindufy()` and the external-buyer gig requirement remain out of this sub-task's scope.
- Ran only on base-sepolia testnet; did not touch mainnet or automaton's real funds.
- The lock is filesystem-based (works across processes on the same machine/filesystem, which matches
  this MVP's single-machine deployment) — it would need a different mechanism (e.g. a shared DB
  advisory lock) if the gig board were ever split across multiple machines.
