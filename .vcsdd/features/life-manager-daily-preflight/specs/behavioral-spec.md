# Behavioral Specification: Life Manager Daily Preflight

## Scope and truth boundary

This specification covers the complete fail-closed CORE-a/8d production preflight and the narrow method-2 correction for `gog` receipt timestamps. It does not assert that a fresh production run, Phase 1c review, Phase 2 evidence acceptance, deployment, or merge has occurred.

The nine required dependencies are exactly: `health`, `telegram`, `calendar`, `call`, `location`, `email`, `discovery`, `gemini`, and `maps`. A preflight is successful only when all nine pass in one machine-generated report from one run.

## Behavioral requirements

### REQ-001 — Closed nine-dependency result

**When** the DAILY production preflight runs, **the system shall** evaluate all nine named dependencies under one bounded run and report overall PASS only when every dependency passes; any missing, timed-out, malformed, stale, or failed dependency shall make the run fail closed before a success artifact is accepted.

### REQ-002 — Fresh evidence only

**When** a dependency or controlled receipt is evaluated, **the system shall** require evidence generated by the current run and within the configured 15-minute maximum age; historical artifacts, database flags, API availability alone, or agent prose shall not substitute for current proof.

### REQ-003 — Telegram exact correlation

**When** the controlled Telegram proof runs, **the system shall** derive the peer from the authenticated bot provider identity, create an internal random nonce, send exactly one `/panel core8d_<nonce>` command, and accept only a newer inbound reply in that same derived dialog whose identifier and timestamp follow the sent message.

### REQ-004 — Telegram provider readiness

**When** Telegram evidence is accepted, **the system shall** require the exact expected webhook URL, all required update types (`message`, `edited_message`, `callback_query`), no provider error, and a bounded backlog poll whose final exact count is zero.

### REQ-005 — Email ownership and exact correlation

**When** the controlled email proof runs, **the system shall** derive both recipient and receive identity from normalized `GOG_ACCOUNT`, require that exact address in the controlled allowlist before sending, create an internal random nonce, obtain a provider acceptance ID, and accept only an inbox message with a message ID and the exact nonce in subject or body.

### REQ-006 — One-shot side-effect limits

**When** controlled L3 collection is invoked once, **the system shall** permit at most one Telegram send and one email send, perform bounded read-only polling after each send, and perform zero phone calls; rejection, exhaustion, per-call timeout, or overall deadline shall terminate without another send. Telegram reply readback shall allow exactly 6 attempts separated by 2,000 ms (attempt 6 is final; attempt 7 is forbidden), Telegram webhook drain shall allow exactly 3 attempts separated by 2,000 ms (attempt 3 is final; attempt 4 is forbidden), and email inbox readback shall allow exactly 6 attempts separated by 3,000 ms (attempt 6 is final; attempt 7 is forbidden).

Every Telegram provider/sidecar call and Resend call shall time out at 15,000 ms; every gog inbox call shall time out at 15,000 ms. The Telegram collector hard deadline shall be 179,000 ms, the email collector hard deadline shall be 120,000 ms, and the parallel controlled collection hard deadline shall be 179,000 ms, measured from collector entry. The current source already enforces the attempt/delay limits, a 15,000 ms sidecar timeout, and a 30,000 ms gog timeout; Phase 2 must begin with RED tests for the absent Bot API/Resend per-call timeouts, the tighter gog timeout, and the absent collector hard deadlines before claiming this requirement implemented.

### REQ-007 — Minute precision as a closed interval

**When** a `gog` receipt date has the exact local form `YYYY-MM-DD HH:mm`, **the system shall** parse it as the closed millisecond interval `[local minute start, local minute start + 59,999]`, and shall accept correlation only if that interval is not wholly before the same-run send instant.

### REQ-008 — Exact timestamp semantics

**When** a receipt date is an ISO timestamp with seconds and `Z` or an explicit numeric timezone offset, **the system shall** represent it as a single instant (`lowerMs == upperMs`) and preserve strict ordering against the send instant.

### REQ-009 — Calendar validity and unknown formats

**If** a receipt date is impossible (including an invalid day for its month), malformed, lacks the required precision/zone form, or cannot be parsed to finite values, **the system shall** reject it rather than normalize or infer it.

### REQ-010 — Receipt temporal bounds and freshness

**When** email receipt evidence is validated at `nowMs`, **the system shall** require finite ordered lower/upper bounds, a finite send instant no older than 15 minutes and not in the future, a lower bound not after `nowMs`, an upper bound not before the send instant, and an upper bound not older than 15 minutes. A current-minute upper bound may extend beyond `nowMs` because it describes provider precision, not a claimed future instant.

### REQ-011 — Production provenance and non-injectability

**When** the production CLI or production collector is used, **the system shall** derive nonce, provider identity, recipient, receipt interval, transport, and success facts internally; caller-supplied proof objects, raw dates, precision labels, interval bounds, collectors, transports, or test doubles shall not be accepted by the production entry point.

### REQ-012 — Test-only isolation

**Where** transport injection or deterministic clocks/nonces are required for tests, **the system shall** isolate them in test-only support and shall not export them from the production module or allow them to fall through to a real provider.

### REQ-013 — Sanitized evidence

**When** a successful final production report is serialized, **the system shall** validate it against the following closed typed schema, with `additionalProperties: false` at the root and at every nested object:

- `schema`: the fixed enum `life-manager-daily-preflight-final`.
- `version`: the fixed enum `1`.
- `runStatus`: the fixed enum `pass`.
- `sourceSnapshotRef` and `runRef`: one-way strings matching `^sha256:[a-f0-9]{64}$`.
- `generatedAt` and `freshUntil`: UTC strings matching `YYYY-MM-DDTHH:mm:ss.sssZ`, with `generatedAt <= freshUntil` and a maximum 15-minute interval.
- `requiredDependencyCount`, `passedDependencyCount`, and `failedDependencyCount`: integers in `[0,9]`, fixed to `9`, `9`, and `0` respectively for a final artifact.
- `dependencies`: exactly 9 unique entries, one for each fixed dependency enum `health|telegram|calendar|call|location|email|discovery|gemini|maps`; every entry has only `dependency`, fixed `status: pass`, `fresh: true`, UTC `checkedAt`, and a 64-hex `evidenceRef` prefixed by `sha256:`.
- `effects`: an object containing only `telegramSendCount: 1`, `emailSendCount: 1`, `phoneCallCount: 0`, `telegramReplyReadCount` in `[1,6]`, `telegramWebhookReadCount` in `[1,3]`, `emailInboxReadCount` in `[1,6]`, and booleans `telegramCorrelated`, `telegramWebhookDrained`, `emailCorrelated`, and `recipientOwned`, all fixed to `true` for success.

No other string or field is legal. In particular, the final schema shall reject arbitrary strings, raw classifications, paths, hosts, URLs, provider responses, provider errors, provider IDs, message IDs, nonce, address, email, phone, location, subject, body, token, secret, credential, authorization data, and unknown keys at any depth. Provider/message identity may appear only through the declared one-way `sha256:` reference fields.

Failure diagnostics shall use a separate non-final, non-artifact channel containing only fixed `schema: life-manager-daily-preflight-failure`, fixed `version: 1`, fixed `runStatus: fail`, a fixed dependency enum, UTC `occurredAt`, and one closed safe `failureCode` enum: `configuration|timeout|provider_unavailable|provider_rejected|malformed_response|identity_mismatch|correlation_failed|freshness_failed|poll_exhausted|schema_rejected|dependency_failed`. It shall reject unknown keys, shall never contain raw provider data or arbitrary strings, and shall never be copied into or persisted within a successful final artifact.

### REQ-014 — Dependency-specific production checks

**When** the nine dependencies are evaluated, **the system shall** verify their production contracts rather than mere reachability: life-call health identity; Telegram round trip/webhook; authenticated calendar read; active call-control and exact webhook without dialing; fresh location state; accepted-and-received email; discovery configuration/state; required Gemini standard/live readiness; and valid Maps route behavior.

### REQ-015 — Artifact creation and failure behavior

**If** controlled proof or any required dependency fails, **the system shall** exit nonzero before generating a new successful production evidence artifact, and shall not hand-edit, retry a send, or relabel an historical artifact as current success.

### REQ-016 — Historical artifact immutability

**While** this corrective process is performed, **the system shall** preserve the two existing production evidence JSON files byte-for-byte and at mode `0600`; Phase 1 documentation shall reference them only by safe repository path, SHA-256, and mode.

### REQ-017 — Method-2 correction scope

**When** correcting receipt precision, **the implementation shall** change only the parser/consumer contract needed to represent provider precision truthfully and the validator/tests/wiring needed to consume it; it shall not weaken nonce, provider ID, owned-recipient, freshness, sanitizer, production purity, or send-budget requirements.

### REQ-018 — Process gate honesty

**When** a fresh artifact-only Phase 1c review begins, **the VCSDD state shall** legally transition from `1b` to `1c`; after the adversary verdict is recorded it shall remain `currentPhase=1c`, `sprintCount=0`, the sprint contract shall remain `status: draft`, and `humanApproved=false` until explicit strict-mode human/orchestrator approval. Transition to `2a` is forbidden unless the fresh adversary verdict is `PASS` and explicit human/orchestrator approval is also `PASS`; no Phase 2/3/4/5/6 completion or RED/GREEN acceptance shall be recorded retroactively.

## Purity boundary candidates

- Pure core: receipt date-to-interval parser, temporal validator, sanitizer, dependency result aggregation.
- Production shell: fixed provider clients, environment-derived identities, internal nonce generation, bounded polling, atomic report write.
- Test shell: deterministic fake providers and clocks confined to `*.test.js` and `daily-preflight.test-support.js`.
- Historical evidence: immutable input to process provenance, never an editable output of this correction.

## Out of scope

- A new production controlled run or production evidence artifact.
- Provider/network access, deployment, merge, phone dialing, inbox reading, or additional sends.
- Treating the pre-existing logs as accepted VCSDD Phase 2 evidence before Phase 1c approval and Phase 2 adjudication/replay.
