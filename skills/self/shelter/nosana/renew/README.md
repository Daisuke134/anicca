# Nosana self-renewal path (S3)

Keeps Franklin's Nosana compute alive with **zero human in the loop** by extending the currently
running job before it expires, paid from Franklin's own wallet. This is S3 of the "agent financial
independence" goal, built on top of S1 (`../deploy.mjs`, first paid job) and S2
(`../funding/acquire-nos.mjs`, self-funded NOS acquisition).

## The vendor CLI cannot renew — verified, not assumed

`nosana job extend <job> -t 15 --wallet <path>` crashes even under a PTY:

```
TypeError: Cannot read properties of undefined (reading 'includes')
    at Command.extendJob (@nosana/cli/dist/src/cli/job/extend/action.js:23:99)
```

Zero funds moved on that attempt. So renewal cannot be a CLI wrapper — it has to go around the CLI
entirely, exactly like `../deploy.mjs` already had to go around `nosana job get`/`job list`'s own
non-interactive crashes.

## The three candidate rails, and which one is verified wallet-only

### 1. `@nosana/kit`'s `client.jobs.extend()` — VERIFIED WALLET-ONLY. Used here.

`@nosana/kit` exposes **two, easily-confused** "extend" surfaces. Only one is wallet-only:

- `client.api.jobs.extend({address, timeout})` — **REJECTED.** This is the credits/API rail.
  Quoting `@nosana/kit`'s own docs (`docs/api/jobs.md`, nosana-ci/nosana-kit):
  > "Jobs are single execution units that can be posted directly using credits, without requiring
  > a deployment." … `POST https://dashboard.k8s.prd.nos.ci/api/jobs/{address}/extend` with
  > `Authorization: Bearer nos_xxx_your_api_key`.

  Nosana credits are bought with a card via Stripe on nosana.io — a human funds the account. If a
  human's card pays the rent, the agent is not independent. `../deploy.mjs` already refuses this
  exact rail for the initial post (`NOSANA_API_KEY`/`NOS_API_KEY` are logged as deliberately
  ignored, never passed through) — this module never even imports `client.api`.

- `client.jobs.extend({job, timeout, payer?})` — **VERIFIED WALLET-ONLY. This is what
  `executor.mjs` uses.** Quoting `@nosana/kit`'s README (nosana-ci/nosana-kit, "Extend Job
  Timeout"):
  > ```ts
  > // Set wallet first
  > client.wallet = yourWallet;
  > // Extend job timeout by 1800 seconds (30 minutes)
  > const instruction = await client.jobs.extend({ job: address('job-address'), timeout: 1800 });
  > // Submit the instruction
  > await client.solana.buildSignAndSend(instruction);
  > ```
  No `api.apiKey` anywhere in this path. Tracing the source confirms it end to end:
  `packages/kit/src/services/programs/jobs/instructions/extend.ts`'s `extend()` calls
  `getRequiredWallet()` (throws `NO_WALLET` if `client.wallet` is unset — there is no API-key
  fallback) and builds `client.getExtendInstruction({..., authority: wallet, payer: wallet, ...})`
  from `@nosana/jobs-program` (the autogenerated on-chain program client) — a plain Solana
  instruction with `authority`/`payer` as `TransactionSigner`s. `client.wallet` is a `KeyPairSigner`
  built via `@solana/kit`'s `createKeyPairSignerFromBytes(secretBytes)` from Franklin's OWN already-
  resolved 64-byte secret (`../keypair.mjs`'s `deriveAddressFromSecret`) — never a new/second
  wallet, never a keyfile on disk. This exact resolution chain — `createNosanaClient()`,
  `client.jobs.extend`, `createKeyPairSignerFromBytes`, `getSignatureFromTransaction`,
  `client.solana.buildTransaction`/`signTransaction`/`sendTransaction` — was resolved for real in
  this repo's own `node_modules` (not just read from docs) before being wired into
  `executor.mjs`'s `defaultBuildAndSignExtend`/`defaultSendSignedExtend`.

### 2. The on-chain jobs program directly (no SDK) — REJECTED as the implementation choice, not as a rail.

`client.jobs.extend()` above **is** rail 2 — it is a thin wrapper that builds the exact same
`getExtendInstruction` from `@nosana/jobs-program`, the on-chain program client, with no API auth
at all. Hand-rolling the same instruction ourselves (bypassing `@nosana/kit`) was considered and
rejected: the extend instruction needs a market lookup, an ATA derivation, and PDA derivations for
`vault`/`rewardsReflection`/`rewardsVault` against Nosana's static program addresses — plumbing
`@nosana/kit`'s own `Instructions.extend()` already implements and tests. Re-deriving it by hand
risks a subtle, hard-to-verify correctness bug (a wrong PDA seed order, a wrong static address) for
no money-safety benefit — `@nosana/kit` is a single well-scoped, officially-maintained dependency
(added to `package.json`; see this feature's report for the exact diff), not a redesign of the
rail.

### 3. Post a fresh job before expiry instead of extending — kept as the FALLBACK, not the primary path.

Nosana's own `SIMPLE-EXTEND` deployment strategy (`docs/deployments/strategies.md`,
nosana-ci/nosana-kit) is described as: "runs the specified number of job replicas, but instead of
terminating the jobs at the end of the timeout period, it extends them for another period equal to
the timeout... until there are no more funds available to run it" — i.e. Nosana's own reference
behavior for "keep this alive" is EXTEND, not repost. `INFINITE` (repost-before-expiry) is
"(COMING SOON)" per the same doc. Reposting also carries a real availability risk extend does not:
the successor could be picked up by a different node after a queueing delay, versus extend keeping
the SAME running job/node with zero gap. `executor.mjs` therefore only reposts (reusing
`../deploy.mjs`'s already-tested `deployNosanaJob`, unchanged) when there is **no alive job left to
extend** — i.e. a lapse already happened — never as a routine substitute for extending.

## What's built here

| File | Role |
|---|---|
| `rent-clock.mjs` | Pure: given real `timeStart`/`timeout` and now, decide `dueForRenewal` with a configurable lead time (default 180s); derives the at-most-once `windowId`. |
| `cost.mjs` | Pure: NOS cost of extending, using the job's own locked-in `price` (raw NOS/sec, read directly off the job account) — not a re-fetched market rate. |
| `survival-drive.mjs` | Pure: NOS balance ÷ NOS/hour burn rate → runway; classifies into `nominal`/`warning`/`critical`/`insolvent` and a `promoteEarning` signal. **Signal only** — wiring it into an actual earn-lane priority system is out of scope here. |
| `job-lookup.mjs` | Real job-state reads over the SAME authoritative, auth-free jobs API `../deploy.mjs` established (`GET .../api/jobs?payer=<wallet>` — never CLI stdout); pure aliveness/selection logic. |
| `executor.mjs` | Orchestrates the above: extend the alive job, or repost via `deployNosanaJob` if none is alive. At-most-once via an intent ledger (`nosana-renewal-intents.jsonl`), reconciling unknown outcomes from real state, never blind-retrying. |
| `../../../../../bin/citizen-rent` | Thin CLI entrypoint — `--dry` (default) / `--live`. |

## Money-safety notes

- **`--dry` is the default.** Every step (identity, balances, real job state, the rent-clock
  decision, the real cost estimate, the spend gate) runs for real; the function returns before any
  on-chain action. Dry mode never touches the intent ledger at all (matches `../deploy.mjs`'s own
  convention).
- **At-most-once.** A live renewal writes an intent row (signature already known, since signing
  happens before sending — mirrors `../funding/acquire-nos.mjs`'s pattern) before any broadcast.
  Before that, the SAME windowId is checked against the ledger: a settled/posted row refuses
  outright; an unresolved intent row triggers reconciliation from real state (the job's own
  on-chain timeout for extend, or a newly-alive successor job's `timeStart` for repost) — never a
  blind retry. See `executor.test.mjs` for the two required proofs: unknown-outcome reconciles
  rather than retries, and one window cannot produce two payments (asserted via call counts on the
  sign/send seams, held to exactly one across two full `renewShelter` invocations).
- **Honest death.** The survival-drive signal is computed and logged on every run regardless of
  whether a renewal is due, so insolvency (`runwayHours <= 0`) is visible even before it blocks a
  renewal outright. A refused gate returns `decision: "refused"` loudly; `bin/citizen-rent` exits
  nonzero for any refused/insolvent/critical/unknown outcome — never a silent success-looking exit.

## Known gap: the live extend call chain is unverified against a real transaction

This session never ran `--live` (explicit instruction — the first real renewal is a human call).
`defaultBuildAndSignExtend`/`defaultSendSignedExtend` in `executor.mjs` were verified by resolving
every function in the real chain against this repo's own installed `@nosana/kit`/`@solana/kit`
(`client.jobs.extend`, `createKeyPairSignerFromBytes`, `client.solana.buildTransaction` /
`signTransaction` / `sendTransaction`, `getSignatureFromTransaction` — all resolve to real
functions, not `undefined`) and by reading `@nosana/kit`'s own README/source for the exact
documented usage — but never exercised end to end against a live transaction. This is the same
kind of documented, best-effort-but-unverified-live gap `../deploy.mjs`'s own README carries for
`nosana job post`'s JSON shape ("Known gap: unverified `nosana job post` JSON shape").
