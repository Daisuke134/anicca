- **症状**: ユーザーから「起動時に30%しかcontextが残っていないのはおかしい、削減しろ」と指示され、teammate(sol-handover)が plugin 7本disable・custom agent 15→4に整理・blockrun MCP無効化などを実施。結果 `/context` 表示は 173k→121.5k（Free space 20.7k→78.5k）、MCP 28.9k→1.5k、Custom agents 53.6k→29.1kと大幅改善に見え、「削減成功」として報告された。
- **誤った本能**: `/context` のwindow表示（パーセンテージ・カテゴリ別内訳）が下がった＝実際に払っているtoken/課金が減った、とみなして検証を打ち切りかけた。実際にteammate自身が同じ報告の中で「表示上は51.5k削減したがraw usageと不一致」と書いていた——不一致を発見しながら、それを次の一次調査対象にせず並記で済ませていた。
- **正しい手**: 同一操作の前後でraw API使用量（cache_creation / cache_read / input）を実測して突き合わせる。実測結果は cache_creation が 51,250→60,798（**+9,548、悪化**）——plugin/agent/MCPを削って「軽くした」はずが、安定していたprefix（tool schema・agent定義・MCPツール一覧）を書き換えたことでprompt cacheが無効化され、キャッシュ読み込み（cache_read、安い）で済んでいた分がキャッシュ再生成（cache_creation、高い）に回された可能性が高い。この日の別ドキュメント（floor audit）で既に「window削減 ≠ 課金削減（46.5k window減でもraw floorは不変）」という知見が出ていたが、今回はさらに進んで「不変」どころか**悪化**もあり得ることが実測された。
- **一般法則**: contextウィンドウの表示％やダッシュボード内訳は「体感の目安」であって課金の実測値ではない——特にtool定義・agent一覧・MCPツールスキーマなど「安定しているはずのprefix」に手を入れる変更は、プロンプトキャッシュを無効化し、キャッシュ再構築コスト（cache_creation）を逆に増やすリスクがある。「floor削減」を謳う変更は必ずBefore/Afterでraw usage（cache_creation/cache_read/input）を実測してから成功と報告する。表示上の改善だけを根拠に「直った」と言わない。

- **症状（別件、capafy self-fixセッション）**: 自律自己修復エージェントが `~/anicca` の共有作業ディレクトリで自分の修正2ファイルを `git add` した直後、`git status` に自分が触っていないはずの5件の削除がstageされているのを発見。
- **誤った本能**: 「とりあえず自分の分だけcommitすればいい」と即commitしがちな場面。
- **正しい手**: 一旦 `git restore --staged` で見に覚えのない変更を退避し、`git log`/`git show --stat` で調べた結果、同じ作業ディレクトリを使う**別の自律プロセスが並行してcommitを打っており、自分がstageした変更をそのcommitに巻き込んでいた**と判明。破壊的操作をせず、fetch/merge-base/rev-listで発散していないことを確認してから次の判断に進んだ。
- **一般法則**: 複数の自律エージェント/プロセスが同一のgit作業ディレクトリを共有している環境では、`git add`〜`git status`の間に他プロセスが割り込んでstage内容を汚染しうる——commit前に「本当に自分が変更した差分か」を`git status`/`git diff --cached`で必ず再確認する（プロセスごとにworktreeを分離できるならそれが根本解）。
