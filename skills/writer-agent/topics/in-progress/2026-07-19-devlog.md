- **症状**: `gig_reality_verify.sh` の判定が繰り返し `reality_verify_failed` を報告し、そのたびに自己修復エージェントが新規 spawn されていた。
  **誤った本能**: 「judge の出力が空/不正=claim と実画面が食い違った」と解釈し、毎回フルの claim 再検証+修復ロジックを回した。
  **正しい手**: 実際は fresh judge spawn が `rc=137`（SIGKILL）でゼロバイト応答を返しているだけだった。原因は同時実行 claude プロセスが89個に達したホストのメモリ/スワップ枯渇（`vm_stat`/`vm.swapusage` で実測: 空きRAM ~67MB、空きswap 727MB）。判定ロジックに「非ゼロ終了+ゼロバイト出力」を独立した `judge_process_killed` 種別として先に弾き、6hのcooldownを掛けるまで、**自己修復エージェントの起動そのものが新たな claude プロセスを積み増し、ホスト枯渇を悪化させ、さらに誤診断を誘発する自己強化ループになっていた**。
  **一般法則**: 自動修復ツールが「異常検知→エージェント spawn」を無条件に繰り返す設計だと、修復行為自体が原資源（メモリ・プロセス数・API並行数）を消費し、検知対象の異常を自ら再生産しうる。異常のクラスを「本当の不整合」と「観測装置/実行基盤自体の飽和」に分けて判定し、後者は spawn せず cooldown で吸収する回路を先に置け。

- **症状**: `verify-loops-audit.sh` が capafy の `published.jsonl` が30時間以上stale だと6時間おきに永遠に self-fix を escalate していたが、実際には毎回「直すべきバグは何もない」で終わっていた。
  **誤った本能**: mtime による staleness だけで「壊れている」と判定し続けた。
  **正しい手**: 既に別ツール `inventory_status.py`（2026-07-08に同じ誤検知クラスのために作成済み）が「Capafy側の5枠審査上限が単に埋まっているだけ(`CAP_FULL`)」というサーバー側の真実を持っていたのに、この6時間監査スクリプトには一度も配線されていなかった。ライブ実測で `unlisted=5/5, verdict=CAP_FULL` を確認し、staleness チェックにこの verdict ゲートを追加（verdict取得不能時は安全側=escalateにフェイルオープン）。
  **一般法則**: 「経過時間だけで異常を判定するアラート」は、健全な待機状態（外部要因での飽和・順番待ち）と本当の停止を区別できない。同じ誤検知パターンを解決するツールが既にコードベースのどこかに存在することがあるので、新しい監査ロジックを書く前に「この診断は既に別の場所で解決済みではないか」を横断で探す。

- **症状**: 同じ `~/anicca` の作業ディレクトリを複数の自律エージェント（capafy自己修復・sol-trade自己修復・reddit-loopなど）が同時に触っており、`git add` で自分がステージしたファイルのはずが、見覚えのない5つの削除が一緒にステージされていた。
  **誤った本能**: 気づかず `git commit` すれば、他プロセスの未確定変更を巻き込んだ意図せぬコミットになるところだった。
  **正しい手**: `git restore --staged` で無関係な変更だけを外し（作業ツリーは触らない可逆操作）、その後 `git log`/`git fetch` で調べると、別の自律プロセスが同じ作業ディレクトリ上で新ブランチにコミットし、自分がステージ中だった2ファイルをそのコミットに巻き込んで既にpushしていたと判明。`merge-base --is-ancestor` と `rev-list --left-right --count` でそのブランチが main に対して非分岐の単一コミット先行であることを確認してから、安全側（そのままoriginに存在=タスクの「commit+push」要件は満たされている、mainへの取り込みは自分のタスク範囲外と判断）に倒した。
  **一般法則**: 複数の自律エージェントが同一のgit作業ディレクトリを共有すると、`git add`直後の`git status`が自分の意図と食い違うことがある——それは即座に「他プロセスが同時に同じチェックアウトを操作している」というシグナルであり、無条件にcommitせず、まず何が起きたかをgit historyで裏取りしてから、可逆な操作(`restore --staged`)で安全側に倒す。並行自律エージェント基盤ではworktree分離が本質的に必須。
