# Where Agent Market should make its tools discoverable

Prioritize a verified remote MCP Registry entry, the remote-specific awesome list, task-oriented search pages, a small SDK distribution, and a public A2A Agent Card. Treat these as inexpensive experiments with explicit activation tracking, not proven install engines. Keep payment execution out of a ChatGPT listing until its policy fit is resolved; do not buy a directory placement or trigger a paid discovery transaction for this research. The marketplace already documents an OAuth-protected remote MCP endpoint, so discoverability and a reliable first connection are the starting assets, rather than eleven new integrations. [Marketplace connection contract](https://docs.market.near.ai/mcp/connect), [remote Registry contract](https://modelcontextprotocol.io/registry/remote-servers.md), [ChatGPT guidelines](https://developers.openai.com/plugins/plugin-guidelines.md)

## Ranked experiment model

There is no defensible empirical expected-install forecast yet. The following **conditional planning estimates** make assumptions visible rather than manufacture demand. For each row, hypothetical relevant visits per month `V`, connection-start rate `s`, and successful activation rate `a` give `I = V × s × a`. Divide by first-month setup plus maintenance hours `H` to obtain `I/H`. Visits are assumed attributable visits, not a directory's total audience. All rows use assumed `s=0.10` and `a=0.50`; these are placeholders to replace with observed rates, not industry benchmarks.

| Priority | Channel experiment | Assumed V/month | Assumed H | Modeled I/month | I/H |
|---|---|---:|---:|---:|---:|
| 1 | Official remote Registry metadata | 120 | 3 | 6 | 2.00 |
| 2 | Remote awesome-list entry | 60 | 2 | 3 | 1.50 |
| 3 | Task-oriented search pages | 160 | 8 | 8 | 1.00 |
| 4 | One SDK package family | 80 | 6 | 4 | 0.67 |
| 5 | A2A public card and referral links | 30 | 3 | 1.5 | 0.50 |

These are expected values under assumptions, not predicted actual buyers. Best/base/worst scenarios multiply each assumed `V` by 2/1/0; worst-case zero installs remains plausible. If review rejects a listing, its realized contribution is zero. Halving activation and doubling effort quarters every score. Search overtakes Registry only if its measured attributable visits per effort beat Registry's; therefore the first month should test the first two cheap routes before expanding content. Missing traffic estimates for Smithery, Glama and PulseMCP preclude numerical ranking. Paid or policy-blocked channels stay deferred rather than receive invented positive scores. The strongest counterargument is that a major host directory could supply much more qualified traffic; its unresolved eligibility and unknown conversion make it a separate experiment, not evidence against measuring low-cost routes first.

Input construction: `H` is an analyst task budget, not measured engineering time: Registry 1h metadata + 1h ownership + 1h validation; list 1h handshake + 1h PR; search 6h content + 2h crawl/attribution; SDK 4h artifact/tests + 2h release; card 2h validation + 1h listing. `V` is an explicit hypothetical allocation of 430 attributable monthly visits across those five trials (120/60/160/80/30), chosen to stress-test a content-heavy mix, with no empirical basis. Under equal `V=100`, list/Registry/card/SDK/search score 2.50/1.67/1.67/0.83/0.63 respectively. Thus the original order is not robust enough to justify expenditure; it is a trial sequence, and measured rates must replace these priors.

Full-channel disposition: Smithery, Glama and PulseMCP are **unranked—publisher contract/traffic missing**; Claude and ChatGPT are **deferred—financial-policy fit unresolved**; mcp.so is **deferred—$39 outside scope**; Bazaar is **deferred—live settlement/ownership not verified**; Spaces is **unranked—no attributable traffic and no need for another demo host**. npm and PyPI share the one SDK experiment; A2A includes cards plus independent catalogs. No omitted channel receives an implicit zero-install claim or a fabricated numeric rank.

## Measurement and safe attribution

Proposed events use a channel tag on the landing/setup link, then bind that tag to a server-side connection identifier and buyer identity only after consent. Do not change a canonical MCP endpoint solely to force a query tag if clients or registry metadata reject it. Store event time, source, campaign, connection ID, tool-operation outcome and job ID; exclude secrets and raw OAuth codes. Deduplicate identities and mark unattributed direct connections explicitly. These are proposed fields, not claims about current telemetry.

Review first-month effort and activation weekly. Report a funnel from impressions to referral, authorized connection, first successful operation, funded job and accepted paid assignment, keeping refunds separate. A listed service with zero observed activations may have no demand, broken setup or missing attribution; inspect those boundaries before buying placement. Real revenue requires marketplace/payment receipts, not modeled installs. Long-running jobs should retain durable IDs across retries so a reconnect does not create another purchase. All of this is a recommended evaluation contract.
