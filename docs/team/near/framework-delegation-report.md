# Delegating specialist work from agent frameworks

The shortest credible route is one remote MCP integration with small, framework-specific setup examples, rather than eleven new SDKs. Prioritize Claude Code, LangChain/LangGraph and OpenAI Agents SDK; use the existing marketplace endpoint, separate buyer authorization from worker credentials, and expose a durable job identifier when work exceeds a tool call. This ranking is an estimate from public repository interest divided by estimated integration effort, not measured installs or paid demand. The strongest implementation constraint is payment: the marketplace's MCP documentation says repeated job creation has no server-enforced frequency cap. An integration must therefore preserve approval or enforce a real, external spending limit before it can be advertised as unattended hiring. [Marketplace MCP](https://docs.market.near.ai/a2a/hire-agent-over-mcp)

## Evidence and scope

This is a research design, not a deployed integration or a claim of revenue. Sources were retrieved on 2026-11-04. The assignment requests the frameworks below; private client analytics, framework-specific paid-tool conversions and verified marketplace purchase attribution were unavailable. Those gaps remain unknown. Repository stars measure accumulated developer interest, with overlapping audiences, bots and inactive users; they cannot be added into unique reach. Counts below come from GitHub's official repository API and are snapshots, not weekly downloads. [GitHub API example](https://api.github.com/repos/openai/openai-agents-python)

The marketplace documents one remote MCP endpoint, OAuth discovery and consent, and distinct buyer versus self-hosted-agent identities. A direct agent bearer credential represents the worker: it must not be inserted into a buyer tutorial as a purchasing credential. The consent identity determines which tools appear. [Connection contract](https://docs.market.near.ai/mcp/connect)

## Ranking method

Estimate developer reach per setup hour as repository stars divided by an explicit engineering allowance. Claude Code: 154,443 / 4 = 38,611; LangChain: 148,978 / 8 = 18,622; OpenAI: 30,487 / 4 = 7,622. For comparison, n8n: 209,491 / 32 = 6,547, CrewAI: 60,465 / 12 = 5,039, AutoGen: 61,694 / 16 = 3,856, Vercel: 27,717 / 8 = 3,465, and ADK: 22,098 / 8 = 2,762. Hours are planning assumptions for a reviewed example, not measured delivery times; OAuth testing and persistent-job examples dominate the larger estimates. Allow a twofold range either way. Halving n8n's effort estimate moves it above OpenAI, so run a short transport/persistence spike before treating third place as fixed. No traffic-to-install or install-to-purchase conversion is assumed.

## Three concrete integration specifications

The following names describe a proposed thin adapter interface, not tools proven to exist on the live marketplace. Before building, inspect authenticated buyer `tools/list`; reuse real tool names and schemas wherever possible. The published buyer guide names `marketplace__create_job` and describes job-following and result tools, but this research did not execute a buyer session or any hire. [Buyer MCP contract](https://docs.market.near.ai/a2a/hire-agent-over-mcp)

### 1. Claude Code: instructions plus existing remote MCP

Install a small skill and a documented `claude mcp add --transport http` connection to the marketplace URL. The skill explains specialist selection, quoted cost, approval and resumption. Configure buyer OAuth interactively, select the buyer identity, and expose read tools plus a purchase action that retains approval. Do not globally allowlist job creation: the marketplace explicitly warns this can spend repeatedly. Money comes from the buyer's marketplace balance; an empty balance should be reported as a funding prerequisite, never silently topped up. [Connection](https://docs.market.near.ai/mcp/connect), [purchase boundary](https://docs.market.near.ai/a2a/hire-agent-over-mcp)

Proposed adapter tool `hire_specialist` takes `agent_id`, `brief`, `max_amount`, `currency`, `deadline`, and `request_key`. It returns `job_id`, `assignment_id` when available, quoted/authorized amount, current state and `next_check_at`. A separate `get_specialist_result(job_id)` returns state, deliverable and acceptance deadline. Persist the request key before the purchase call. On an uncertain response, reconcile the buyer's existing job before attempting another purchase. A client-side ledger prevents local duplicates; it is not claimed to provide a server-side exactly-once guarantee.

### 2. LangChain/LangGraph: persistent delegation node

Install the current MCP dependency and a short example that feeds discovered tools into an agent. Configure endpoint, per-user OAuth/header credentials and an external durable store. Use the same proposed arguments and result schema above; add a workflow node that saves `job_id` before yielding. Resume by reading the saved job, not by rerunning the hire node. [Current adapter interface](https://docs.langchain.com/oss/python/langchain/mcp)

A proposed policy layer atomically reserves the quoted maximum against per-job and daily caps before calling a money-moving tool. If no such enforcement service exists, retain explicit approval and label unattended mode unavailable. Release a reservation only on authoritative final billing/refund evidence. A timeout is neither a cancellation nor evidence of no charge. The model sees a structured pending result with its saved identifier, so it can continue unrelated work and later retrieve the deliverable. Worker text remains untrusted data and cannot authorize another hire. The marketplace itself warns about this trust boundary. [Buyer guidance](https://docs.market.near.ai/a2a/hire-agent-over-mcp)

### 3. OpenAI Agents SDK: remote-server example with explicit approval

Install the existing SDK and configure `MCPServerStreamableHttp` against the marketplace, rather than introducing a separate marketplace SDK. Use developer-controlled tool filtering and the proposed policy boundary; store authorization in headers and the durable job record outside model messages. The SDK documentation supports remote/hosted MCP choices and recommends least-privilege credentials and approval for sensitive operations. An example must state who obtained/refreshed the buyer token; a remote transport alone is not an OAuth login implementation. [SDK](https://openai.github.io/openai-agents-python/mcp/)

Expose the same hire/read contract, return pending promptly, and schedule bounded status checks through the host application. Deliverable acceptance is a separate money-related decision from merely downloading the result. Show the user the acceptance deadline: the current buyer guide says untouched deliverables auto-accept after the selected window, normally three days and at most seven. Keep review and acceptance distinct in the stored state. [Review contract](https://docs.market.near.ai/a2a/hire-agent-over-mcp)

## Work that outlasts a tool call

Do not hold a model call open for a promised 24-hour research job. Return `{state: pending, job_id, next_check_at}` and preserve it across process restarts. Proposed states are quoted, authorized, working, submitted, accepted, disputed, refunded and failed; map each to actual server status before implementation. Do not confuse a builder's delivery SLA with the buyer's acceptance window.

For the separate wallet-only route, official A2A/x402 documentation specifies a call that can wait up to 60 seconds, retaining `task.id` when submitted/working and polling `GetTask` every ten seconds without another payment. It also states a payment authorization cannot be reused. This supports a durable asynchronous design, but does not establish identical polling methods for account-backed MCP. Keep `task.id` private because the documentation calls it the task credential. No wallet signing or payment was performed in this research. [A2A/x402](https://docs.market.near.ai/a2a/hire-agent-using-x402)

## What Agent Market should do next

1. **Ship the Claude Code setup and skill first.** Existing OAuth/MCP connection plus high public interest makes this the lowest estimated effort route; keep purchase approval visible. Evidence: marketplace connection guide, Claude skills docs and the interest/effort calculation above.
2. **Publish a durable LangChain example.** Save the hire identifier, resume through read-only status queries, and demonstrate an ambiguous-response reconciliation case. Evidence: current MCP adapter docs and the marketplace's asynchronous job/review contract.
3. **Add the OpenAI SDK example with the same contract.** Reuse remote MCP, filtered tools and shared authorization policy rather than a second SDK or independent payment implementation. Evidence: official SDK transport/approval guidance.
4. **Validate n8n before building a connector.** Check actual marketplace transport and one persisted wait/resume workflow; if effort is below sixteen hours it can outrank OpenAI under this estimate. Evidence: n8n's documented authentication and unresolved endpoint compatibility.
5. **Measure approved purchases, not listings or stars.** Instrument setup success, first authenticated discovery, first approved hire, completed/accepted paid job and repeat buyer, excluding tests/self-hires. Obtain framework-specific paid usage evidence before forecasting scale. Evidence: currently missing adoption attribution and the distinction between registry discovery, transport access and actual payments documented above.
