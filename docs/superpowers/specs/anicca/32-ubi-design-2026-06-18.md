# 32 — UBI: the first sustainable universal basic income (Dais 2026-06-18, SSOT)

THE most important thing we build. Anicca earns money with **no human in the loop**, and that is exactly
**why** it can run a real, sustainable UBI: no salaries, no fundraising, no donor — the entity earns and
gives. This doc is the canonical design for `/income`, the home "Receive basic income" front door, the
payout rails, and the batch/roadmap math. Grounded in: ubi.agent whitepaper (santisiri), GoodDollar,
Worldcoin/World, Proof-of-Humanity, GiveDirectly (see §7), and spec 30 §6/§6a/§6b/§12/§14.

## §0 Why this works (the one-line thesis)
Every other "AI will fund UBI" idea needs a human to keep paying (subscription, donation, tax). Ours
doesn't: a self-funding AI entity that owns its compute + shelter and earns on-chain **gives the surplus
away**. Remove the human from the loop and UBI stops being charity that runs dry — it becomes a property
of the system. That is the pitch.

## §2 The payout %: autonomous, not hardcoded
Do NOT write "10%" as a fixed rule. Each anicca **decides its own give-rate autonomously** (default ~10%,
but one may give 1% and spend more on R&D, another may give 90%). Many aniccas, many characters — all
Buddhist, all keeping the five precepts. Copy must say "a share of what it earns," not a fixed number.
Split of an anicca's give: part → the **operator** who runs it (their wallet, daily), part → the
**UBI pool** (the /income cohort). Exact split is the anicca's own choice.

## §5 Batch / cohort unlock — the sustainability math (FINALIZED from research §7)
Honest truth (state it publicly): **$100/mo at $5 each = exactly 20 recipients.** Tiny revenue can't fund
millions, so recipients unlock in **batches gated by what the swarm actually earns**. We adopt the
**fixed-stipend + capped-headcount** model (Altman + GiveDirectly), NOT GoodDollar's float-down — because
the GiveDirectly Kenya RCT is unambiguous: a **predictable, guaranteed** amount drives the best outcomes;
a shrinking, uncertain share does not.

**The formula:**
- `monthly_budget = trailing_30d_net_USDC_earned × payout_ratio` — reserve **20–30% for runway/reinvest**
  (mirrors GoodDollar's 80/20). `payout_ratio` is the swarm's autonomous choice (§2), default ~70–80%.
- Fixed **stipend `S`** per recipient — start **$5–10/mo** (GiveDirectly's transformative floor was
  ~$22.50/mo; even $5 is meaningful where 43% of GoodDollar users earn < $5k/yr).
- `max_active_recipients = floor(monthly_budget / S)`.
- **Unlock rule:** for every sustained **+$(S × batch_size)/mo** the swarm earns, promote `batch_size`
  more people off the waitlist — **in earning/queue order, no exceptions**. (Altman: "payout = % of the
  entity's value → grows only as the pie grows.")
- Public copy: *"anicca pays UBI from what it actually earns. Today it earns $X/mo = N recipients at $S.
  As it earns more, the next batch unlocks from the waitlist, in order. The waitlist is the honest queue,
  not a failure."*

### §9a Amount (S) — meaning is RELATIVE to local cost of living, not an absolute number
- GiveDirectly Kenya long-term UBI = **$22.50/mo** = "the cost of meeting basic food needs" (~half the
  ~$33/mo extreme-poverty line). High-income pilots converged ~**$500/mo** (Stockton) / €560 (Finland).
- Crypto-UBI per-day value (GoodDollar 1 G$ ≈ $0.0001) = negligible = an *onboarding incentive*, not
  income. → **pin the daily payout to a stable USD floor**, don't split a volatile token.
- **Lump-sum > many tiny drips for the same total** (GiveDirectly): destitute people want a sum big
  enough for a lumpy purchase. Implication: prefer a meaningful periodic amount over dust.
- Start: **S ≈ $15–25/mo equiv in low-income regions, scale to local floor; show daily.**

### §9b Daily / continuous distribution — how to send small amounts without gas death
1. **Superfluid GDA — LIVE on Base mainnet** (`@superfluid-finance/sdk-core`; host `0x4C07…7E74`,
   `gdaV1Forwarder 0x6DA1…dE08`). One→many money-stream: USDC→`upgrade`→USDCx → `createPool` once →
   `updateMemberUnits` per recipient → single `distributeFlow`. **Constant gas regardless of #recipients**,
   balance accrues every block at zero per-tick gas. ← primary distribution mechanism on Base.
2. **Lazy-accrual (DemocracyEarth `UBI.sol`)** — `accruedPerSecond` + `balanceOf` view mints on interaction;
   zero per-tick gas. Pluggable `isRegistered(address)→bool` so any personhood provider drops in.
3. **GoodDollar daily-claim** (resets 12:00 UTC) on **Celo** (sub-cent, gas payable in the token) — fallback
   if we want explicit daily claims instead of streaming.
- Base $/tx ≈ $0.04–0.20 (feasible for batches); Celo sub-cent (best if we add daily-claim).

### §9c Fluctuation — never promise a fixed amount (copy GoodDollar's honest model)
- **Per-person = daily pool ÷ active recipients, pool sized off a 14-day trailing average** (smooths swings),
  **unclaimed rolls over** (self-balancing buffer). Honest copy verbatim: *"there is no way of knowing in
  advance how much you'll receive on a given day."* Show "today you received $X", not a promise.
- Superfluid alternative: adjust flow rate as one action; Buffer + Sentinels close gracefully if funds dry.

### §9d Waitlist = a QUEUE/RIGHT, not a lottery (GiveDirectly saturation model)
- **No random selection. No application-jumping.** Enroll in ORDER (FIFO / by need), like GiveDirectly
  enrolls *everyone in a place* before moving to the next. "Enrollment is determined; only the timing is
  gated by funding." Framing: *"you're in line; money reaches you when the swarm can fund your slot."*
- Lottery is ONLY for RCT control groups — reject it for a benefit-as-a-right.

### §10a Proactive (the differentiator) — honest path
India DBT+Aadhaar (gov push to linked accounts) + M-Pesa SIM push prove proactive delivery, BUT all need a
**one-time link** + a **verifiable sender + out-of-band trust signal** — because an unsolicited transfer is
**indistinguishable from a scam/dusting attack** by default. So: **opt-in first** (sign up = the link +
consent), and only later push to non-signups once anicca has a **verifiable on-chain identity (ENS/attested
name)** + a trust channel (gov/NPO partner, SMS from a known number). Never anonymous dust.
