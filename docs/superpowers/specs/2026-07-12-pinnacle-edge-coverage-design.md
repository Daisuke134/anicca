# Pinnacle-vs-Polymarket エッジ検出のカバー範囲設計

日付: 2026-07-12
対象: `~/anicca/skills/earn/polymarket-trade/pinnacle_edge.py`（既に動作中）

## なぜこれをやるのか

claude-p が実際に利益を出した取引は、すべて「調べてから片側に賭けた」ものだった。Polymarket 公式 data-api で全取引を検証した結果、directional（調査して片側）が **4戦4勝 +$9.78**、bundle arb（両建て裁定）は **+$0.24** にすぎない。稼ぎの98%は調査由来である。

そして `pick.py` が永遠に WAIT していた理由は資本ではなく情報だった。`ai_analyzer.py::consensus_analysis()` は LLM に「市場の質問文」と「市場自身の現在価格」しか渡していない。外部情報がゼロの LLM は、目の前の価格を上回る推定を出せない。

`pinnacle_edge.py` はその欠けていた情報源を入れる。Pinnacle は勝つ客を締め出さず、vig 1-3%、ラインはプロの syndicate が形成する——公開されている中で真の確率に最も近い。Polymarket は retail の板で反応が遅い。両者が食い違うとき、その食い違い自体がエッジであり、**試合の予測を一切必要としない**（より鋭い予測者を写すだけ）。

## 現状の問題（実測）

| 段階 | 件数 |
|---|---|
| The Odds API `upcoming` で取得 | 23イベント |
| → 試合前のみ（in-play/終了を除外） | 8件 |
| → Polymarket に同じ試合が存在 | **2件** |
| → エッジ ≥3pt | **0件** |

母数が足りない。調査では MLB/NBA で1-5%の乖離が1日複数回発生するとされるが、2件では出会えない。

## 計測して分かった事実（2026-07-12、実 API）

1. **Gamma API（Polymarket、無料・無制限）は offset でページングできる**
   - `limit` は 100 が上限（500 を指定しても 100 しか返らない）
   - 5ページ取得 → ユニーク **497市場 / 71試合**（従来は 100市場 / 34試合しか見ていなかった）

2. **The Odds API はスポーツ別エンドポイントの方が圧倒的に効率が良い**
   - `upcoming`（1 credit）→ 23イベント、試合前 8件
   - `baseball_mlb`（1 credit）→ 19試合、試合前 **14件**

3. **Polymarket が実際に持つスポーツは3つに集中している**（出来高上位の実測）
   - サッカー（`soccer_fifa_world_cup` — Argentina vs Switzerland が $7.5M）
   - UFC/MMA（`mma_mixed_martial_arts`）
   - MLB（`baseball_mlb`）

4. **`/v4/sports`（一覧）は credit を消費しない**（レスポンスヘッダ `x-requests-last: 0` で確認）

5. **残 credit = 492 / 500（月次）**

## 設計

### 中核の原理：無料側から駆動する

Polymarket 側（Gamma）は無料・無制限なので**先に全部取る**。The Odds API は 1 credit/スポーツなので、**Polymarket が実際に持っているスポーツにだけ credit を使う**。

```
① Gamma を offset でページング（無料）
     → 開いている全市場（~500）→ 「A vs B」形式の試合（~71）

② その試合が属するスポーツにだけ Odds API を叩く（3 credits）
     baseball_mlb / mma_mixed_martial_arts / soccer_fifa_world_cup

③ 突合 → Pinnacle の no-vig 確率 vs Polymarket の価格
     乖離 ≥ min_edge の側だけを機会として報告
```

### credit 予算ガード（機械的強制）

無料枠 500/月 = **16.6 credits/日**。3スポーツ × 1 credit = 3 credits/スキャンなので、**1日5スキャンが上限**（15 credits/日 = 450/月）。

ループは 20-90分ごとに起きるため、放置すれば月枠を数日で使い切る。したがって **`pinnacle_edge.py` 自身が最小フェッチ間隔を強制する**（ディスクにキャッシュし、間隔内の再フェッチを拒否して前回結果を返す）。これはプロンプトでのお願いではなく、コードによる強制とする——散文のルールが守られないことは、このプロジェクトで実証済みである。

- `PINNACLE_MIN_FETCH_INTERVAL_S`（既定 4.5時間 = 16200秒）→ 1日約5スキャン
- キャッシュ: `<skill>/state/pinnacle-cache.json`（fetch時刻 + 生レスポンス）
- credit 残量はレスポンスヘッダ `x-requests-remaining` から読み、状態に記録して観測可能にする

### 既に実装済みの安全装置（初回ライブ実行で発見した罠に対応）

1. **試合前フィルタ（`is_prematch`）**
   初回実行で「+97,147% のエッジ」が出た。McKinney が Polymarket $0.0005 に対し Pinnacle 48.6%。**これは罠だった**——試合が既に始まって彼が負け、市場が0に再値付けした一方、Pinnacle のラインが試合前のまま残っていただけ。買えば全額失っていた。開始済みの試合は両者が比較不能なので除外する。

2. **異常値フィルタ（`max_edge`、既定 30pt）**
   Pinnacle も Polymarket も流動性があり professional に見られている。真の乖離は数pt であって 30pt ではない。巨大な「エッジ」は、ほぼ確実に「同じ生の状態を見ていない」（決着済み・古いライン・誤マッチ）ことの証拠であり、一撃で全額失う唯一のクラスの信号である。捨てることに実質コストはない。

3. **fail-closed**
   突合できない／読み取り失敗／片側欠落は、すべて「機会なし」として扱う。推測で埋めない。

## この設計が守る原則

- **エンジンは判断しない。** サイズも「賭けるか」も決めず、乖離を報告するだけ。決めるのは呼び出し側（pick.py / ループ）。
- **推測しない。** 値が取れない、突合できない、時刻が読めない → すべて「機会なし」。誤って高く見積もれば、使えない金で賭けが解禁されてしまう。
- **予算は機械で守る。** 「使いすぎないように気をつける」は守られない。コードが拒否する。

## 検証（実装後にやること）

1. 実 API でスキャンし、**試合前の突合件数が 2件 → 30件以上**に増えることを確認
2. 乖離の分布を実測し、**本当に 3pt 以上の乖離が出るのか**を正直に記録する（出なければ「このエッジは現状存在しない」と結論する。無理に賭けない）
3. credit 消費が 1スキャン = 3 credits であることをヘッダで確認
4. 最小フェッチ間隔ガードが実際にキャッシュを返すことを確認

## 次の段階（この spec の範囲外）

- 実際に 3pt 以上の乖離が出たら、**少額（$1-3）で1回だけ実弾検証する**
- 検証できたら `pick.py` に組み込み、ループが毎 wake 自律的にスキャン→賭ける形にする
