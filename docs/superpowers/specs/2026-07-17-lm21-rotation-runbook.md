READ-ONLY research artifact. No rotation was performed. No secret values appear below.

## 0. Scope note (found during research, not in the original 13)

Grep confirms **`SUPABASE_SERVICE_ROLE_KEY` is consumed by TWO deployed services**, not just
Railway `life-call`: it's read by `apps/life-call/{server.js,scheduler.js,skill-life-manager/scripts/tick.js,scripts/e2e-ask.js,lib/telegram-reply.js}`
**and** by ~21 Netlify functions under `apps/landing/netlify/functions/*.js` (alarm-demo,
income-signup, self-cancel, telemetry, income-apply, income-webhook, alarm-profile,
calendar-connect, stripe-fashion-webhook, alarm-webhook, admin-bank, lm-onboard,
retreat-application, stripe-spawn-webhook, lead-magnet, gmail-connect, webhook, unipile-connect,
loco-ingest, unipile-notify, cafe-waitlist, dashboard-sync). Both point at the **same Supabase
project** (both read `lm_users` / related tables). **This key must be updated in BOTH Railway
and Netlify env vars in the same rotation window**, or the two services diverge on which key is
valid.

Also found: **`COMPOSIO_API_KEY` and `LM_UID_SECRET` are shared the same way** — Railway
`life-call` (server.js) AND several Netlify functions (`lm-onboard.js`, `gmail-connect.js`,
`unipile-connect.js`, `calendar-connect.js` for Composio) read the identical env var name. Same
two-target rule applies.

No `.github/workflows/*.yml` file references any of the 13 keys (grep returned zero matches) —
GitHub Actions is not a rotation consumer here; only Railway (`life-call`) and Netlify (`landing`)
are.

## 2. Ordered runbook

**Principle**: for every provider-issued key that supports old+new coexistence (Supabase, Gemini,
Resend — confirmed; Telnyx, Groq, Composio — assumed dashboard key-list pattern but not
individually confirmed), mint the new credential FIRST, deploy it, verify, THEN revoke the old
one. For the 4 self-minted HMACs and the Telegram pair, coordinate mint+deploy+re-register in one
tight window since there's no natural coexistence period.

### Phase 1 — Mint new credentials (no deploy yet, ~30-45 min, zero downtime)
1. Supabase: Dashboard → Settings → API Keys → create new `sb_secret_...` key (keep legacy `service_role` active).
2. Telnyx: portal.telnyx.com/#/app/api-keys → create new V2 key (keep old active).
3. Gemini: aistudio.google.com/apikey → generate new key (keep old active).
4. Groq: console.groq.com/keys → create new key. **First check `railway variables list -s life-call` and `netlify env:list` (or Netlify UI) to confirm `GROQ_API_KEY` even exists as a deployed var — if not, this is a dashboard-only revoke, no app-side step.**
5. Resend: `POST /api-keys` → new key (keep old active until Phase 4).
6. Stripe: **first**, in the Dashboard, enumerate all webhook endpoints and confirm how many distinct endpoints map to `STRIPE_WEBHOOK_SECRET` across life-call vs. landing (see risk note above) before rolling anything.
7. Unipile / Composio: mint new key via each dashboard (no confirmed old+new coexistence — verify by checking whether the dashboard lets you see/copy the old key value again after creating a new one; if not, this pair may be closer to instant-cutover).
8. Generate the 4 self-minted secrets: `LM_CALL_SECRET`, `LM_UID_SECRET`, `LM_TELEGRAM_WEBHOOK_SECRET`, `LM_INBOUND_SECRET` — `openssl rand -hex 32` each.
9. BotFather: `/token` on the life-call bot → new `LM_TELEGRAM_BOT_TOKEN` (this one likely IS instant-cutover per BotFather's design — old token dies immediately).

### Phase 2 — Set new values in Railway (life-call) and Netlify (landing) together
10. `railway variable set KEY=value -s life-call -e production` for every key that life-call consumes (all 13, per the per-key table's consumer column). Setting a var triggers an automatic redeploy unless `--skip-deploys` is passed — for the self-minted HMACs and `LM_TELEGRAM_BOT_TOKEN`/`LM_TELEGRAM_WEBHOOK_SECRET`, batch-set them all first with `--skip-deploys`, THEN do one `railway redeploy -s life-call -y` so all of them land in the same deploy (avoids partial-rotation states where e.g. the new bot token is live but the new webhook secret isn't yet).
11. In parallel, update the Netlify env vars for the ~7 shared keys (`SUPABASE_SERVICE_ROLE_KEY`, `COMPOSIO_API_KEY`, `LM_UID_SECRET`, `RESEND_API_KEY`, `STRIPE_WEBHOOK_SECRET` if shared, `UNIPILE_TOKEN`) via Netlify dashboard or `netlify env:set`, then trigger a Netlify redeploy of `apps/landing`.
12. Update Resend's inbound-route webhook URL to carry the new `LM_INBOUND_SECRET` query param (Resend dashboard — outside this repo).

### Phase 3 — Re-register what needs re-registration (must happen right after Phase 2's deploy lands)
13. Re-run `setWebhook(NEW_BOT_TOKEN, webhookUrl, NEW_WEBHOOK_SECRET)` — since no code path does this automatically, run it as a one-off script (e.g. `node -e "require('./lib/telegram').setWebhook(process.env.LM_TELEGRAM_BOT_TOKEN, 'https://<life-call-host>/api/telegram/webhook', process.env.LM_TELEGRAM_WEBHOOK_SECRET)"` against the live Railway env, or a raw curl). **This is the step most likely to be forgotten** — the bot will silently stop responding otherwise, with no error surfaced to Dais unless someone messages it and gets nothing back.

### Phase 4 — Smoke checks (immediately after Phase 3)
14. `GET /health` on the life-call Railway URL (confirm the process is up post-redeploy).
15. Send `/start` (or any message) to the Telegram bot from a real Telegram account → confirm a reply arrives (validates new bot token + new webhook secret + setWebhook re-registration all at once).
16. Trigger one real `/lm` onboarding round-trip (or, for an already-onboarded test user, hit `gmail-connect.js`/`unipile-connect.js` with their existing stored `uid`+`sig`) to confirm `LM_UID_SECRET` rotation didn't 403 real users — if it does 403, that confirms the front-end persists old `sig` values and every onboarded user needs one fresh `/lm` visit.
17. Place one real test dial via `lib/dial.js`'s call path (preflight balance check + actual `placeCall`) to confirm `TELNYX_API_KEY` + `LM_CALL_SECRET` + `GEMINI_API_KEY` all work together on the voice bridge.
18. Send one Stripe test webhook event (Stripe CLI `stripe trigger` against each of the (up to 3) endpoints identified in Phase 1 step 6) to confirm signature verification passes with the new secret(s).
19. Send one real inbound-reply-style email hitting the `LM_INBOUND_SECRET`-gated route to confirm the Resend-side URL update took effect.

### Phase 5 — Revoke old credentials (only after ALL Phase 4 checks pass)
20. Disable/delete the old Supabase `service_role` key, old Telnyx key, old Gemini key, old Groq key, old Resend key, old Composio key, old Unipile token, and roll off the old Stripe webhook secret(s) in their respective dashboards.
21. Update `docs/STATUS.md` / the LM-21 task with the rotation completion timestamp and mark old-key-revocation done.

## 3. Downtime impact summary

| Step | Downtime? | Expected duration |
|---|---|---|
| Phase 1 (minting) | None | N/A — old keys still valid |
| Phase 2 (Railway/Netlify redeploy) | Brief — Railway/Netlify cold-start during redeploy | Seconds to ~1 min (Railway restart, per `restartPolicyType=ON_FAILURE` in `railway.toml`) |
| Phase 3, step 13 (setWebhook re-run) | **Telegram bot unresponsive** between "new webhook secret deployed" and "setWebhook re-run completes" | Should be seconds if run immediately after Phase 2; open-ended if forgotten (this is the highest operational risk in this whole runbook, since there's no automated retry/alerting for it) |
| `LM_UID_SECRET` rotation specifically | Every already-onboarded user with a stored old `sig` gets 403 on their next `/lm`-family request until they get a fresh signed link | Unknown duration — depends on the un-audited front-end's re-mint behavior; worst case is "every user must click through Google OAuth again" |
| Stripe webhook secret rotation | Failed signature verification for events arriving in the gap between old-secret-invalid and new-secret-deployed | Stripe auto-retries failed deliveries per its documented retry policy, so no event is permanently lost, but real-time entitlement updates (e.g. `applyBilling` on `checkout.session.completed`) could lag until a retry succeeds |
| `LM_INBOUND_SECRET` rotation | Inbound reply emails 403 until both Railway var AND Resend-side URL are updated | Depends on how quickly both sides are synced — no auto-retry from Resend confirmed for this webhook |

## 4. HONESTY

Confirmed from official docs (cited inline above): Supabase key coexistence
([supabase.com/docs/guides/getting-started/api-keys](https://supabase.com/docs/guides/getting-started/api-keys)),
Gemini's documented rotate-without-downtime procedure
([ai.google.dev/gemini-api/docs/api-key](https://ai.google.dev/gemini-api/docs/api-key)), Telnyx
portal-only key management (Telnyx's own `llms.txt` agent-facing doc), Telegram BotFather `/token`
regeneration (`core.telegram.org/bots/features`), Telegram `setWebhook`'s `secret_token` param
(inferred from the existing `lib/telegram.js` code, which is first-party, not docs — but matches
Telegram's own Bot API naming), Stripe's automatic webhook retry behavior
(`docs.stripe.com/webhooks`), Resend's documented `POST /api-keys` create endpoint
(`resend.com/docs/api-reference/api-keys/create-api-key`), and Composio's dashboard-only,
three-key-type auth model (`docs.composio.dev/reference/authenticating-to-composio`).

**Could NOT confirm from docs (flagged individually above too):**
- Whether Telnyx's portal supports multiple *simultaneously active* API keys (old+new coexistence) — inferred from "API Keys" being a list UI, not stated explicitly.
- Resend's `DELETE /api-keys/{id}` endpoint body/parameters — the page fetched empty; I only have the endpoint's existence from the docs nav listing, not confirmation of its exact behavior.
- Stripe: whether "Roll secret" in the Dashboard is instant-cutover (single active secret per endpoint) or supports a grace period — the API reference page required an authenticated session to render, so I could not fetch its body. This is standard/widely-known Stripe behavior (single active secret per webhook endpoint) but I'm not citing a doc URL I actually fetched for that specific claim, only for the retry-behavior claim.
- Unipile's API token rotation mechanics entirely — no key-management doc page found via `llms.txt` index; the "rotating the token doesn't break already-linked accounts" claim is my own inference from their API's `account_id`-based addressing, not a confirmed doc statement.
- Whether Composio's OAuth "auth configs" truly survive a project API key rotation — inferred from their docs describing them as architecturally separate systems, not an explicit "rotation is safe" statement.
- **The single largest unconfirmed risk in this whole runbook**: whether the `/lm` front-end (not in this backend-only scan — it's presumably a separate static page or app under `apps/landing`, not scanned here) persists `uid`+`sig` client-side indefinitely, or re-mints a fresh `sig` on each visit. This determines whether `LM_UID_SECRET` rotation is a non-event or breaks every existing user's saved link. **Recommend checking the actual `/lm` frontend source before executing this rotation**, or accept the worst case and warn users in advance via Telegram broadcast.
- Whether `STRIPE_WEBHOOK_SECRET` truly holds the same or different values across the Railway life-call deploy and the Netlify landing deploy — grep only proves the same *variable name* is read in 3 files across 2 services; it cannot prove or disprove whether they're configured with the same *value* in each platform's env store. Needs a live check of both Railway's and Netlify's dashboards, and Stripe's webhook endpoint list, which I did not have access to in this read-only research pass.
