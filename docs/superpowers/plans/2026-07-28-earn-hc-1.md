# EARN-HC-1 Earning Rail Health Implementation Plan

**Goal:** Every required earning slot and the four portfolio rails (`PM`, `x402`, `WORK`, `CAPITAL`) return one machine-readable state — `operational`, `degraded`, `frozen`, or `not-live` — with fresh evidence. The production registry contains zero `instrumented:false` entries and the live report contains zero `NOT-INSTRUMENTED` results.

**Architecture:** Extend the existing `skills/self/earning-health-registry.json`; do not create a competing registry. Keep the existing trace-barren self-heal path for PM/SOL, add explicit probe contracts for HTTP, heartbeat, funded-account, and disabled rails, and aggregate slot results into the four portfolio rails. Probe output is evidence, not revenue: zero buyers or zero trades does not make a healthy mechanism degraded.

**State contract:** `operational` means the mechanism can accept work now; `degraded` means configured but a required probe is stale/failing; `frozen` means an intentional money-safety stop; `not-live` means deliberately unconfigured/unfunded/unloaded. Unknown or malformed probe results fail closed to `degraded`, never to `operational`.

**Primary-source basis:**

- Kubernetes distinguishes readiness from liveness: “Readiness probes determine when a container is ready to accept traffic.”  
  https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/
- Kubernetes condition records carry a finite status, probe time, and machine-readable reason: status is `True`, `False`, or `Unknown`; fields include `lastProbeTime` and `reason`.  
  https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-conditions

The local four-state vocabulary is the approved Life Manager SSOT contract; the source above supplies the probe/evidence pattern, not the product names.
