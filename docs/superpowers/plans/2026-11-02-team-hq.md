# Team HQ 実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 既存部屋に実働する受信/引き継ぎとCodex定期仕事を接続し、その実証を公開する。
**Architecture:** 既存pollerとLoop runtimeを再利用する。軽量な受信/永続状態は決定的コード、仕事の選択/相談はagentが行う。新チャット・新モデル基盤を導入しない。
**Tech Stack:** Python標準ライブラリ、Slack Web API、既存Codex CLI、Life Manager loop runtime、既存Next blog。
**Spec:** ../specs/2026-09-25-life-manager-unified-ssot.md の TEAM-HQ 節。順序/完了状態の正本は同節。

## Global Constraints
- 既存effect/owner/leaseを保護。秘密とruntime stateはGit外。
- 通常判断/反映/公開は委任済み。新たな承認gateを設けない。
- Codex CLIのmodel固定なし。commandはshell文字列でなくargvで実行。
- main由来immutable releaseから限定反映し、公式readbackで受入。

## Review Focus
- Slack APIがHTTP 200でもok:falseなら成功扱いしない。
- 実行後/送信前のcrashで仕事を再実行しない。
- 送信応答不明はthreadを照合し、再送をblind retryしない。
- 古いthread返信/ページ境界を受信cursorで落とさない。
- トークン不足/無応答時に相手を稼働中と誤認しない。

## Task 1: HQ受信をcanonical sourceへ
Files: runtime/team_hq/、同tests、必要最小のbin/config、既存TEAM-HQ仕様。
- 旧pollerの呼び出し経路、state、lock、schedulerを確認。
- API失敗/再実行/古いthreadのfocused失敗testを先に作る。
- 既存stateを保持する最小入口と永続実行状態を実装。
- focused testとloop contract、diffを確認しcommit/push。
- fresh read-only review→CI/main→immutable release→owner限定apply→自然返信と重複0。

## Task 2: 日次仕事とチーム引き継ぎ
Files: 同HQ runtimeのprompt/config、既存registry/カードへの接続。
- 正確な本人宛先と受信/wake能力を公式応答で確認。
- 受領/着手/最終活動/次操作/証拠を既存taskに対応付ける。
- 日次Codex仕事を既存ownerと突き合わせて設定。未応答/実行中/枠不足を別状態にする。
- focused test、自然run、実成果物、Slack readbackで確認しcommit/push/CI/main/release。

## Task 3: Build in public
Files: docs/research/manager/publication内の既存package、必要なblog bridge pin。
- 成功記事の導入/図/手順/CTAを一次資料と成果指標で照合。
- 今回の実測のみで記事と図を作成。未知と限界を明記。
- content/rendererの既存testとfresh read-only公開review。
- canonical/mainとpublishing bridgeを反映、公式URL/画像をreadback。
- 公開desktop/mobileを目視し、読者に伝わらない箇所を直す。
