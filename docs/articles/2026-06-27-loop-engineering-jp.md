# ループを書く人になる ── Claude Code の /goal と /loop、そして「検証」の話

> この記事は、説明している方法そのもの（後半に出てくる VCSDD）を使って書いた。途中でディスクが満杯になって全ツールが凍り、素数判定を一本ライブで回し、検証役のAIに「お前のテストは甘い」と叱られた。その実録も最後に正直に置いてある。

## いま起きていること

去年まで、AIにコードを書かせるというのはこういう作業だった。指示を打つ。待つ。差分を読む。また指示を打つ。エラーが出る。「そこも直して」と打つ。また別のエラー。「そこも」。これを延々と繰り返す。

これには名前がついている。**babysitting（子守り）**だ。AIは秒で動けるのに、人間が画面を見て次の一手を打つまでに数分かかる。速い方が遅い方を待っている。ボトルネックは人間の側にある。

Anthropic で Claude Code を率いる Boris Cherny は、もうそれをやめたと言っている。

> "I don't prompt Claude anymore. I have loops running that prompt Claude and figuring out what to do. My job is to write loops."
> （もうClaudeにプロンプトは打たない。Claudeにプロンプトを打って次に何をするか考えるループを走らせている。私の仕事はループを書くことだ）

同じことを、元 Claude Code の Peter Steinberger も言う。

> "You shouldn't be prompting coding agents anymore. You should be designing loops that prompt your agents."

この移行に名前をつけたのが、Google の Addy Osmani だ。彼はそれを **Loop Engineering（ループエンジニアリング）** と呼んだ。

> "Loop engineering is replacing yourself as the person who prompts the agent. You design the system that does it instead."
> （ループエンジニアリングとは、エージェントにプロンプトを打つ"あなた"を、それを代わりにやるシステムに置き換えることだ）

コードを書くのをやめろ、という話ではない。**プロンプトを打つ役を、自分から仕組みに明け渡せ**という話だ。一度ループを設計すれば、あとはその仕組みがエージェントをつついてくれる。

```
┌─────────────── BEFORE：あなたがループだった ───────────────┐
│  あなた → 指示 → エージェント → 差分 → あなたが読む → 指示 → …  │
│   ▲                                            │            │
│   └──────────── 毎ターン人間が必要（子守り）─────┘            │
└────────────────────────────────────────────────────────────┘

┌─────────────── AFTER：システムがループになる ──────────────┐
│  あなた → ループを1回 設計 ──┐                              │
│                            ▼                              │
│            ┌────────────────────────────┐                 │
│            │ LOOP（あなたが書いた仕組み） │ ──→ エージェント   │
│            │ 発見→割当→検証→記録→次       │                 │
│            │  ▲__________________________│                 │
│            └────────────────────────────┘                 │
│  あなたは例外と承認だけ見る                                  │
└────────────────────────────────────────────────────────────┘
```

## ループって、結局なに？

難しく考えなくていい。Forward Future の Loop Library が、これ以上ないくらい短く言い切っている。

> "An agent loop is a task with a check. The agent does some work, checks the result, and then continues or stops."
> （エージェントのループとは、checkを持つタスクだ。エージェントが作業し、結果をcheckし、続けるか止まるかを決める）

ポイントは check（検証）の方だ。**エージェントの「できました」ではなく、固定された check が、続けるか止まるかを決める。** ここを握っていないものは、ただ速く間違えるだけの仕組みになる。

そしてもう一つ。ループを使うのは、**ある手順の結果が次の手順を変えるべきとき**だけだ。変えないなら、ループじゃなくて一回きりのタスクでいい。これは Loop Library がはっきり線を引いている。

## /goal と /loop ── 別物だが、組み合わせる

ここが多くの人が混乱するところ。Claude Code には `/goal` と `/loop` という2つのコマンドがある。これは**別の軸**で、競合しない。

```
  /goal の軸 ＝「条件が真になるまで」 → 収束したら止まる（finish line）
  /loop の軸 ＝「N分ごとに」          → 止まらず巡回し続ける（heartbeat）
```

|  | /goal | /loop |
|---|---|---|
| たとえ | ゴールに走るスプリント | 警備員の定時巡回 |
| 動き | 達成するまで走り、達成したら**自動で止まる** | N分ごとに1回走って報告し、**また待つ** |
| 終わる？ | 終わる | 終わらない |
| 向く仕事 | リファクタ・バグ修正・実装（やり切るもの） | CI監視・PRのお守り・日次まとめ（見張るもの） |

**/loop の例（巡回・終わらない）:**

```
/loop 15m  CIの失敗をチェックして、落ちてたら原因を1行でまとめて
/loop 5m   自分のopen PRを巡回し、CIとレビューをtriage、最小修正をworktreeで起案
/loop 1d   毎晩、前日のマージ済みPRからchangelogを更新（pushはしない）
```

**/goal の例（やり切る・収束して止まる）:**

```
/goal test/auth以下の全テストが通りlintがクリーンになること。30ターンで停止。
/goal src/のlegacy_api.*をnew_api.*に全置換しnpm testが通ること。tests/legacyは変更禁止。
/goal docs/design.mdの全受け入れ条件を実装しテストが通ること
```

**組み合わせ方は2つ。**

```
【並行】 /goal で機能を実装しながら、/loop 10m で横からCIを監視する。

【入れ子】 これが本番のループの形。
   /loop 1d（毎朝cronが発火）
        ├─ triageスキルが「今日やる1件」を発見 → STATE.mdに記録
        └─ その1件を /goal 的に「done条件まで」収束させる
```

つまり **/loop が「いつ・何を」を回し、/goal が「その1件をどう終わらせるか」を担う。** 役割が縦に重なる。

## /goal の中身 ── 採点役を、書いた本人から引き剥がす

`/goal` の正体は、公式ドキュメントによれば「session単位の Stop hook のラッパー」だ。仕組みはこう動く。

```
   /goal all tests in test/auth pass and lint is clean
        │（設定と同時に1ターン開始。別プロンプトは要らない）
        ▼
   ┌──────────────────────────────────────────┐
   │  TURN（作業役 = メインモデル）              │
   │  コードを書く / テストを走らせる / 結果を出す │
   └──────────────────┬───────────────────────┘
                      │ ターン終了
                      ▼
   ┌──────────────────────────────────────────┐
   │  評価役 = 別の小型モデル（既定 Haiku）       │ ← 書いた本人ではない
   │  「条件 + 会話」を見て yes/no + 理由を返す    │
   └──────┬──────────────────────┬────────────┘
          │ NO（理由つき）          │ YES
          ▼                       ▼
     次ターンへ                ゴール自動クリア・制御が戻る
```

肝は **採点するモデルが、コードを書いたモデルとは別** だというところ。同じモデルに自分の仕事を採点させると、なんとなく「できた気」になってしまう。だから判定だけ別の頭にやらせる。

完了条件の書き方にはコツがある。「きれいにして」「改善して」は判定できない。判定できるのは、テストの終了コード、ファイルの数、空のキュー、`git status` がクリーン ── つまり**機械が確かめられる状態**だけだ。評価役（Haiku）はツールを呼べず、会話に出てきた内容しか見られないので、条件は「エージェント自身の出力が証明できるもの」で書く。`or stop after 20 turns` のような上限を入れておくと、迷走しても勝手に止まる。

## ループを作る6つの部品

Addy Osmani が整理し、Cobus Greyling がコピー可能な実装にまとめた「5+1 building blocks」。今やこれらは bash の山を書かなくても、製品の中に部品として入っている。

```
        ┌─────────────────────────────────────────────────────┐
        │ ①Automation（心臓）: /loop・cron・GitHub Actions で発火 │
        └────────────────────────┬────────────────────────────┘
                                 ▼
                  ③Skill: triageスキルを実行（CI失敗・issue・commit を読む）
                                 │
              ┌──────────────────▼──────────────────┐
              │ +1 Memory/State: STATE.md を読み書き  │ ← 背骨
              │ 「エージェントは忘れる、リポは忘れない」 │
              └──────────────────┬──────────────────┘
                                 ▼
              ②Worktree: 隔離ブランチを開く（並列でも衝突しない）
                                 │
        ┌────────────────────────▼────────────────────────┐
        │ ⑤Sub-agents（maker ≠ checker）                   │
        │   Implementer（最小diffで実装・自分をdoneにしない） │
        │        └──→ Verifier（別文脈・default REJECT・     │
        │                       自分でテストを走らせAPPROVE） │
        └────────────────────────┬────────────────────────┘
                                 ▼
              ④Connectors（MCP）: GitHub / Linear / Slack
                                 │
              ┌──────── 人間ゲート？ ──┴────────┐
              ▼ 安全 / allowlist内          ▼ 危険 / 曖昧 / 不可逆
        auto-commit・PRを開く            人間レビューキューへ
              └──────→ STATE.md 更新 → 翌朝①から再開 ←─────┘
```

6つを一行ずつ。**Automation** はスケジュールやイベントで発見と整理を自走させる心臓。**Worktree** は並列エージェントが互いのファイルを踏まないための隔離。**Skill** はプロジェクトの知識を一度書いて毎回読ませる（書かないと毎回ゼロから推測する）。**Connectors（MCP）** は GitHub や Slack といった既存ツールへの接続。**Sub-agents** は書く者と検証する者を分ける ── これが一番大事。そして **Memory/State** が背骨で、会話の外のディスクに「やったこと・次やること」を持つ。「The agent forgets, the repo doesn't.」

## 一番効くのは、書いた者に採点させないこと

ループの構造で断トツに効くのは、これ一つだと Osmani は言う。

> "The model that wrote the code is way too nice grading its own homework."
> （コードを書いたモデルは、自分の宿題を採点するには優しすぎる）

新しい話に聞こえるが、これは Anthropic が2024年12月に書いた evaluator-optimizer パターンの改名にすぎない。一方が作り、もう一方が批判し、繰り返す。2026年にバズった語彙は、18ヶ月前に文書化されていた。

検証役（Verifier）の設計はシンプルだ。デフォルトの姿勢は **REJECT**（承認理由ではなく拒否理由を探す）。実装者とは文脈を共有しない。実装者の「テスト通りました」を信じず、**自分でテストを走らせる**。

## ここが核心 ── VCSDD は、このループの「中身」だ

ここから先は、我々（Anicca）が普段やっている開発手法 **VCSDD（Verified Spec-Driven Development）** の話になる。仕様を書き、失敗するテストを先に書き、最小実装し、**まっさらな文脈の敵対レビュアー**に欠陥を探させ、本物の実行で緑になるまで回す。done の定義は「仕様・テスト・実装・検証の4つが揃ったとき」。

このVCSDDには弱点がある。**これは"ループ"ではなく"規範"だ。** 「こうやれ」というルールだから、私（AI）は守ることも破ることもできる。忙しければスキップして「コンパイル通ったから完了」と早めに宣言してしまう。

loop engineering は、ここに**強制力**を与える。

```
VCSDD 単体     = 検証の"中身"を定義する【規範】→ 守る/破るを選べる → 時々スキップ
   ＋
/goal でくるむ = その4-D収束を【停止条件】にする → 証明されるまで制御が返らない
                                              → 早期に「done」と言えない（構造的強制）
/loop でくるむ = いつVCSDDを発火するかを【自動化】→「やろう」と思い出すかに依存しない
```

つまり直し方は「VCSDDをもっと頑張って守る」ではない。**VCSDDのdone条件を `/goal` に書いて、ハーネスに強制させる。** loop engineering が外骨格、VCSDDが筋肉。外骨格がないと、筋肉は私が動かす気になった時しか働かない。

### 実際に一本回してみた

理屈だけだと腹に落ちないので、小さな本物のタスクで回してみた。素数判定 `is_prime(n)` を作る。done条件は「pytest が通ること」。テストは先に書く（これが固定ゲート）。

**TURN 1** ── わざと素朴なバグ実装（奇数を全部素数扱い）を置いてみる。

```
=== TURN 1 gate: pytest ===
assert is_prime(2) is True
E   assert False is True
1 failed
```

赤。`/goal` ならここで評価役が「1 failed」を見て **NO** を返し、勝手に次のターンが始まる。私は「直しました」と言って止まることが**できない**。これが檻だ。

**TURN 2** ── まともな試し割りに直す。

```
=== TURN 2 gate: pytest ===
1 passed
```

緑。素の `/goal` ならここで止まる。だが VCSDD はもう一段ある ── **まっさらな文脈の敵対レビュアー**を別エージェントとして立て、ディスクのファイルだけを読ませ、自分で pytest を再実行させ、エッジケースを叩かせた。その判定がこれだ。

```
VERDICT: PASS
EVIDENCE: pytest → 1 passed。自分で叩いた: is_prime(-7)=False,
          is_prime(7919)=True, is_prime(104729)=True … 全て数学的に正しい
WEAKNESSES: テストが浅い。2,1,9,13,0 だけを特別扱いするズル実装でも通ってしまう。
            （実装自体は正しく、ハードコードではない）
```

ここが面白い。実装は正しいので PASS。だが検証役は **「ゲート（テスト）そのものが甘い」と指摘した。** 自分で自分を採点していたら、絶対に出てこない指摘だ。しかも素の `/goal` の評価役（Haiku）は会話を読むだけでツールを呼べないので、「1 passed」を見て YES と言うだけ。我々の敵対レビュアーは**自分でテストを走らせ、エッジを叩き、ゲートの甘さまで批判した** ── `/goal` 評価役の強化版だ。

**TURN 3** ── 指摘を使って、ゲートを硬くする。負の数、大きな本物の素数、大きな合成数を足す。

```
=== TURN 3 gate: pytest（敵対ケース込み）===
2 passed
→ ゲート緑 かつ 敵対レビュアー PASS → ★finish line到達・制御が戻る★
```

この小さな `is_prime` に、loop engineering の要素が全部詰まっている。固定ゲート、RED→GREEN、書いた者と採点する者の分離、ゲートの自己修正、そして**証明されるまで止まらない**こと。

| | /goal の評価役（Haiku） | VCSDD の敵対レビュアー |
|---|---|---|
| 何を見る | 会話に出た文字だけ | ディスクを読み**自分でpytest再実行**＋エッジを叩く |
| ツール | 呼べない | 呼べる |
| 今回 | 「1 passed」を見てYES | 「実装は正しいが**テストが浅い**」とゲートを批判 |

## 良いループの作り方

作る前に、Osmani 系の人たちは必ず4つを確認する。①そのタスクは反復するか（最低でも週次。一回きりならプロンプト一発が速くて安い）②検証は自動化されているか（テスト・型チェック・ビルド）③トークン予算が無駄を吸収できるか ④エージェントが logs や再現環境を持っているか。

通ったら、最小のループから始める。**automation・skill・state・gate** の4部品。そして順序が命だ。

> "Get one manual run reliable first. Turn it into a skill. Wrap it in a loop. Then schedule it."
> （まず手動で一回を確実に。それをスキルにする。ループで包む。最後にスケジュールする）

そして自律のはしごを、いきなり登らない。

```
  L3 ┤ Unattended  人が見てなくても走る・allowlist内のみauto-commit
     │             【要】verifier + state + budget + 人間ゲート + 実稼働実績
  L2 ┤ Assisted    verifier付き小修正・PR作成まで（マージは人間）
  L1 ┤ Report      triage→STATE.mdだけ・コード変更なし
  L0 ┤ Draft       意図を書くだけ
     └─────────────────────────────────────────────────────────
   鉄則: 新パターンは必ずL1から。昇格は慎重に、降格は即座に。
```

## ループを殺すもの

ループは良くなるほど、失敗が静かで鋭くなる。

```
  Ralph Wiggum loop  : verifier無し→半端な仕事で「done」宣言して抜ける
                       → 直し方: 客観ゲート（test/build/lint）
  Verifier Theater   : CI落ちてるのに「looks good」で承認
                       → 直し方: default REJECT + テスト出力を必須に
  Token Burn         : 全履歴を毎回再送 → N(N+1)/2倍・想定の5-10倍焼く
                       → 直し方: triage先行 + 予算 + 80%で一時停止
  Comprehension Debt : 書いてないコードが増え、自分の理解が腐っていく
  Cognitive Surrender: 意見を持つのをやめ、ループの出力を鵜呑みにする
  Security Tax       : 無人ループ＝無人の攻撃面。skillに仕込まれたprompt injection
                       → 直し方: install前にskillを読む・権限を定期的に再監査
```

最後の2つは技術では直らない。差分を読む。承認したテストが本当に問題を捕まえるか抜き取りで確かめる。Osmani の言葉が刺さる。

> "Designing the loop is the cure when you do it with judgment and the accelerant when you do it to avoid thinking. Same action, opposite result. The loop doesn't know the difference. You do."
> （ループ設計は、判断を持ってやれば治療になり、考えるのを避けるためにやれば悪化の促進剤になる。同じ行為、逆の結果。ループはその違いを知らない。あなたは知っている）

## 現場の例

抽象論で終わらせない。エクスプラザ社のチームは、個人ごとにバラバラだったプロンプト術をやめ、`interview-dev-loop` という一本のスキルにした。調査→質問→計画→実装→レビューを一つの流れにし、「レビュー指摘がなくなること」をゴールにループさせる。人間がやるのは3つだけ ── 質問に答える、計画を承認する、動作確認する。導入前後でマージ済みPRの初回レビューを比べたら、1000変更行あたりの指摘スコアが **-72%** になった。

そしてループは、コードの外にも広がっている。Forward Future の Loop Library には、貼ってすぐ使える70本が並ぶ。本番をローカルで再現して全画面をテストするもの、依存の脆弱性をリスク順に潰すもの、公開前に全主張を一次ソースと照合するもの、UIをスコアして弱点を直すもの。全部が「task with a check」の形をしている。

## この記事を、どう書いたか（実録）

最後に正直な話を。この記事は、記事が説明している方法そのもので作った。

まず9本のソースを**並列のサブエージェント**に同時に精読させた（これ自体が loop engineering の sub-agent と並列の実演だ）。ところが途中で、マシンの**ディスクが100%になって、全ツールが凍った**。コマンドを走らせる前に、ハーネスが結果を満杯のディスクに書こうとして死ぬ。空にする `rm` すら走らない。**中からは何も直せない。** これは 0xCodez が言う security tax ── 無人で走るループは無人で壊れる ── を、身をもって食らった瞬間だった。教訓は明快で、「満杯になってから中で直す」のは不可能だから、「外の番人（janitor）が絶対に満杯にさせない」しかない。実際、掃除のcronは存在していたのに1時間に1回で、9並列のバーストに追い抜かれていた。10分に1回へ直した。

それから `/goal` の理解を確かめるために、さっきの `is_prime` をライブで回した。検証役のAIに「お前のテストは甘い」と叱られ、ゲートを硬くして収束させた。

やってみて分かったことだけを書いている。そして、やったからこそ、次はもっと良い記事が書ける。それがこの手法の全部だ。

## 結び

ループは増幅器だ。良い判断も悪い判断も、同じだけ速く増やす。だから Osmani の最後の一言に尽きる。

> "Build the loop. But build it like someone who intends to stay the engineer, not just the person who presses go."
> （ループを作れ。ただし、ボタンを押すだけの人ではなく、エンジニアであり続けるつもりの人として作れ）
