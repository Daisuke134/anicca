## 1. なぜP05-2が必要なのか

P05-1のOntologyは、人物・目的・行動・結果などの関係を**意味として**扱う。P05-2はその意味を、**実際のイベントIDで、再現可能・監査可能に追跡する**ことを学ぶ。

最終的にManagerが問いに答えたい：

1. どのモデルが、どの観測から、何を予測したか？
2. 何を候補にして、どの比較と制約のもとで意思決定したか？
3. 実行したのか？ 許可は有効だったのか？ 重複実行したのか？
4. 提供者は何を受理／返信したか？
5. 独立した測定で何を確認できたか？
6. その結果を「Managerの介入が原因」と言える研究デザインがあるか？
7. 判断時点で**本当に知ることができたデータだけ**を使っていたか？

この7問のうち最後3問を誤れば、AIの自己申告やソフトウェアの送信成功を「人間の苦しみを減らした証拠」に誤昇格させてしまう。

## 2. 正本は既に存在している：読むべきファイル

- `runtime/contracts/common-record.schema.json` — Draft 2020-12の**既存共通契約**。Job, RuntimeEvent, Effect, Receiptなどを定義。**本研究でファイル変更なし。**
- `runtime/loop/runtime_event.py` — `validate_runtime_event()`。省略できないフィールド、機微情報、時刻、ID、診断項目の同時存在などを検査。
- `products/manager/manager_core/evidence_types.py` — `Prediction`は`proof_level=P0`, `human_outcome=NOT_MEASURED`, `causal_support=False`。AI予測に本物の実結果を帰属できない。
- `products/manager/manager_core/models/intervention.py` — `InterventionPlan`には`NO_ACTION`が必須。根拠不十分なら何もしない。
- `products/manager/manager_core/verifier.py` — 提供者Receiptとは別のExternalReadbackが必要。ただし教材の読取は`VERIFIED_FIXTURE_ONLY`を超えない。
- `products/manager/manager_core/outbox.py`, `authority.py` — 本番の操作・権限・再送防止・停止はここが所有し、Graphや研究アダプタには発行させない。

**重要：** 既存`Job.effect_key`と`Effect.effect_id`は別のID。JobをEffectとつなぐには、前者と`Effect.idempotency_key`の同一性、`loop_id`の同一性を確認し、Effect→Receiptでは`effect_id`・`run_id`・`loop_id`・`provider`を検証する必要がある。

## 3. 既存の型・IDを具体的に見る

| 正本の型 | 重要フィールド | P05-2での役割 |
|---|---|---|
| Job | `tenant_id,job_id,loop_id,effect_class,effect_key` | 誰の仕事で、どの操作クラスと重複防止キーを使うか |
| Effect | `effect_id,run_id,idempotency_key,provider,attempted_at` | どの操作を、いつ実行しようとしたか |
| Receipt | `receipt_id,effect_id,run_id,provider,recorded_at,outcome` | 提供者からの返答、成功・失敗・不明など |
| RuntimeEvent | `event_id,run_id,phase,status,provider_receipt_id,official_readback_ref` | 実行・検証・報告の経緯。参照URLだけで独立した効果を証明しない |
| Prediction型 | `source_refs,model_id,distribution,proof_level` | モデルの出力はP0。**現在の共通契約には正規のprediction_idは存在しない** |
| InterventionPlan型 | `option_id,action,cost,risk,expected_effect` | 選択肢とNO_ACTION。**現在の共通契約には正規のdecision_idは存在しない** |

`experiment_id`も既存の4種の運用レコードでは共通必須フィールドではない。したがって、P05-2ではこれらのIDを**架空の正規IDとして勝手に捏造しない**。読み取り結果には`null`と「未接続ギャップ」を明示した。

## 4. 数学：時点ごとの情報の集合

知識を受け取った時刻を`recorded_at`、イベントの観測や実施時刻を`event_time`とする。

判断時点`t`で使用可能な根拠：

\[
\mathcal{I}(t)=\{e\mid e.\text{known\_at}\le t\}.
\]

途中のログが不完全でも、真の世界から空白を補完してはいけない。たとえば09:00の仕事に対し、09:01のReceiptが存在しても、09:00の判断にそのReceiptを使うと後知恵リークになる。

コードでは、**既存のJobに独立の発生時刻／run_idがないことも明示**。Jobだけが見えていてEffectがまだ無い場合、ジョブを特定run_idへ勝手に結合しない。今回の`pre_effect`のlinked recordが0なのは「ジョブがなかった」という意味ではなく、「そのrunへの確実な接続がまだない」ことを示す。

## 5. コードを順に読む：読み取り専用でExisting Contractを再利用

成果物：`experiments/p05_2_evidence_trace.py`

### 5-1. 既存schemaの読み込み

```python
SCHEMA_PATH = ROOT / "runtime" / "contracts" / "common-record.schema.json"
SCHEMA = json.loads(SCHEMA_PATH.read_text(encoding="utf-8"))
VALIDATOR = Draft202012Validator(SCHEMA, format_checker=FormatChecker())
```

- 最初の行は、既存のJSON Schemaへの場所を指定する。
- 次はJSONファイルをPython辞書へ読み込む。
- `Draft202012Validator`は、その辞書のルールに従ってレコードが妥当か検査する。
- `FormatChecker`はdate-timeなどの書式チェックを追加する。
- 新しい共通Schemaを作るのでなく、**既存の契約をそのまま使用している**。

### 5-2. 元の正規レコードを読み取り専用で扱う

```python
@dataclass(frozen=True)
class StampedRecord:
    kind: str
    record: dict
    known_at: str
    source_ref: str
```

`@dataclass`は定型のデータクラスを簡潔に定義する機能。`frozen=True`は外側の属性値を再代入できないようにする。

ただし`record: dict`の**内部は変更できてしまう**ため、コードではバイト表現由来のSHA256も保持し、後から変更されていないか検査する。`frozen`だけで安全だと勘違いしてはいけない。

`known_at`はその情報をシステムが知った時刻。`source_ref`は何の元記録から受け取ったかを示す。今回は人工URIだけを扱う。

### 5-3. Joinの厳密な条件

```python
effect["idempotency_key"] == job["effect_key"]
effect["loop_id"] == job["loop_id"]
receipt["effect_id"] == effect["effect_id"]
receipt["run_id"] == effect["run_id"]
receipt["provider"] == effect["provider"]
```

違う人、違う実行、違うサービスから来たレコードを、時刻が似ているという理由でつなげない。

さらに、tenantのスコープ、RuntimeEventの`job_id`と`owner_id`、重複レコード、別runからのReceiptの衝突も検査する。

### 5-4. 真実の階層を混同しない

最終的に返すのは`manager.research.read_only_trace.v0`という**研究用の表示ビュー**。

```json
{
  "action_permission": "NEVER_ISSUED_BY_TRACE",
  "can_execute": false,
  "can_prove_causal_effect": false
}
```

送信を実行できる権限を追加したり、Receiptの有無だけで介入成功を認定する機能はない。

## 6. 実際に人工イベントを動かした結果

実験に使った事前定義の4種の記録は、Job→Effect→Receipt→RuntimeEvent。全部**完全人工データ**であり、実サービスには一切送信していない。

| 知識のCutoff | 追跡で安全に結べた記録数 | 解釈 |
|---|---:|---|
| 09:00:00 | 0 | run_idと結びつける根拠がまだ足りない |
| 09:00:10 | 2 | JobとEffectが結びつく |
| 09:04:00 | 4 | ReceiptとRuntimeEventも見える |
| その後 | 4 | 人間の実際の成果は未測定のまま |

後からReceiptが届くケースも別に検査した。最初はReceiptを見せず、記録時刻を超えた時点でのみ結合する。

どの時点でも`can_prove_causal_effect=false`。`NO_ACTION`の選択が既存Manager Coreで維持されることも確認している。

## 8. P05-2における設計判断

1. **最小の設計**：共通スキーマの変更ではなく、既存レコードを検証するread-onlyのCorrelation Traceから始める。
2. **欠落は欠落のまま**：正規の`prediction_id`/`decision_id`/`experiment_id`がないことを明確に記録。追加が必要なら各Producerとの互換性テストと移行計画を作る。
3. **証拠がないときはNO_ACTION**：当該研究のTraceが権限を発行することはない。
4. **Live GETだけは別のレイヤ**：Listen Labsの調査APIへのアクセス実績は、行動モデルの実性能や介入価値を証明しない。
5. **新しい本番機能はまだ未投入**：本実験の成功を既存の実行エンジンや全事業の更新と混同しない。
