## 0｜この講義の結論（まず読む）

**巨大なManager独自のOntology・graph database・実行基盤をゼロから実装しない。** すでにある以下を組み合わせる。

1. **人間行動の概念**：COM-B（Capability / Opportunity / Motivation → Behaviour）、BCTTv1（93技法）、BCIO（介入・文脈・対象者・評価）。

3. **時点と観測**：source ledger / official readbackを正本とする、読み取り専用のtime-aware projection。空白・未知・推測を勝手に「事実」にしない。

5. **モデルの独自研究対象**：予測分布、反実仮想の推定、部分観測の状態更新、介入選択、不確実性・外部検証。これらは既存のデータ標準を作り直すこととは別の挑戦。

## 1｜何をOntologyと呼ぶのか：5つの概念を区別

**Ontology（オントロジー）**は「何という種類のものがあり、何がどんな関係を持てるか」を共有する**意味の設計図**。実世界に関する事実が存在することの証明ではない。

`Person, Goal, Context, State, Observation, Intervention, Action, Outcome, Measurement, Evidence, Consent`などがどの種類の対象で、`observedFrom`や`proposedFor`などの関係を持つかを定義する。

**Knowledge Graph**は、その定義に沿って実際の観測・推測・実行記録から組み立てる**主張のグラフ**。図に線を描いたからその関係が真になるのではない。

**状態表現（State Representation）**は、ある意思決定時点に知ることができた情報と、推定した不可視の心理・行動状態。

**Digital Twin**は、特定の対象について履歴から状態を更新し、新しい状況・時間・介入で反応を予測し、独立データで検証される**動的なモデル**。単なる個人プロフィール、擬人化したLLMペルソナ、あるいは知識グラフそのものを「検証済みDigital Twin」と呼ばない。

**Executor**は、選ばれた操作を権限・費用・停止条件に従って実行する仕組み。モデルが`CAN_EXECUTE`と書いたり、グラフに`authorized`の矢印を描いたりしても実行権限は発生しない。

> 重要：`世界モデルの正確さ`・`人間に似ていること`・`真の因果効果の識別`・`実際に役に立つこと`は異なる測定対象。

## 2｜基本的な数式：何をモデル化するのか

一時点の単純な状態ベクトルを

\[
s_t=(\text{goal},\text{history},\text{context},\text{motivation},\text{fatigue},\ldots)
\]

と書いても、モチベーションなどは直接は観測できない。観測`o_t`（行動ログ、回答、各種センサ）と、介入`a_t`を分ける必要がある。

\[
o_t\sim p(o_t\mid s_t),\qquad
s_{t+1}\sim p(s_{t+1}\mid s_t,a_t).
\]

意思決定側にあるのは観測済みの真の`s_t`とは限らず、**信念状態（belief state）**：

\[
b_t(s)=P(s_t=s\mid o_{\le t},a_{<t}).
\]

介入のWhat-ifを考えるときはさらに

\[
p(o_{t+1}\mid do(a_t=a),\mathcal H_t)
\]

という**因果的な反実仮想**が必要。どれだけ細かいOntologyを作っても、交換可能性やpositivityを自動的に満たすことはない。

Managerの型は、少なくとも`ObservedFact`、`InferredState`、`PredictedOutcome`、`InterventionCandidate`、`AuthorizedAction`、`ExecutionReceipt`、`IndependentOutcome`、`EstimatedCausalEffect`の意味を分ける。単なる型の列挙でなく、元のデータ・日時・使用条件を必須とする。

## 3｜行動科学：既存研究を再利用する

### COM-B

Michie, van Stralen & West (2011)のCOM-Bは、人間の行動がCapability（能力）、Opportunity（機会）、Motivation（動機）によって生まれるという有力な行動設計枠組み。これらを心理変数の**真値**と決めつけず、行動変容仮説の説明・コード化に活用する。

出典：Behaviour Change Wheel, Implementation Science (2011) https://pubmed.ncbi.nlm.nih.gov/21513547/

### BCT Taxonomy v1

Michie et al. (2013) のBCTTv1には**16グループ・93の行動変容技法**があり、介入内容の「有効成分」を共通語で記述できる。通知はただのUI通知ではなく、何の介入技法か、いつ、誰へ、どの程度提供したかを明示したい。技法の存在は実際の効果を保証しない。

出典：https://pubmed.ncbi.nlm.nih.gov/23512568/ ／ https://www.bct-taxonomy.com/

### BCIO — 最優先で学習・マッピングすべき既存Ontology

Behaviour Change Intervention Ontology（BCIO）は介入内容・提供方法・対象集団・環境・結果と評価を結び、「何が・誰に・どんな文脈で・どれほど効くか」を表現するために開発された。2025年時点のBioPortal上には公開OWLがあり、研究プログラムHuman Behaviour-Change Project（HBCP）が推進する。

出典：https://bioportal.bioontology.org/ontologies/BCIO ／ https://www.humanbehaviourchange.org/

**最重要の先行例**：Hastings et al.の禁煙介入効果予測研究（公開版2025）。**405件のRCT報告・971研究アーム・82特徴量**をBCIOで表現し、未知条件の禁煙率を予測。五分割CVのMAEはOntology-informed rules **9.15パーセントポイント**、比較のDeep Neural Network **9.42**、Random Forest **9.53**、mixed-effect linear regression **10.55**。これは**禁煙率の予測誤差**であり、未見RCTでの個別化CATEや「介入したらどれくらい改善した」という効果差の正確さを直接証明した値ではない。研究の識別・サンプル分割・介入群と比較群の情報など、詳しい設定に依存する。

出典：Hastings et al., *Predicting outcomes of smoking cessation interventions in novel scenarios using ontology-informed, interpretable machine learning* https://pmc.ncbi.nlm.nih.gov/articles/PMC12603517/

HBCP自身も、研究報告に欠落や曖昧さが多く、詳細な自動抽出を完全に行うことは現時点で難しいと述べている。**だからOntologyを入れれば自動的に真実が得られるわけではない。**
出典：https://www.humanbehaviourchange.org/hbcp-findings

### JITAI・MRT

Nahum-Shani et al. (2018)のJITAI（Just-in-Time Adaptive Intervention）は、**Decision Points（意思決定時点）／Intervention Options（選択肢）／Tailoring Variables（適応変数）／Decision Rules（選択規則）**を中心に定義する。まさにOntologyで区別しておきたい要素。短期のProximal Outcomeと長期のDistal Outcomeも分ける。MRT（Micro-Randomized Trials）は逐次介入の効果を適切に検証する設計。

出典：https://pmc.ncbi.nlm.nih.gov/articles/PMC5364076/ ／ https://academic.oup.com/jamia/article/26/3/198/5260831

### 観測事実のために2種類の時間を必ず分離する

**Valid time**：事実が実世界でいつ適用されたか。`valid_from`など。

**Recorded time / transaction time**：システムがその情報をいつ取得したか。`recorded_at`。

例：10:00の行動を14:00に初めて把握した場合、12:00時点のManagerの意思決定にその情報を利用できたことにしてはいけない。**後から分かった情報を過去の予測へ漏らすことは因果・ベンチマークの根幹を壊す。**

Graphiti / Zepの時間付きfactも有力な参考実装。Zep自体は、`valid_at`や`invalid_at`が導出された時間範囲であり、真実性の証明ではないと明示する。

出典：https://help.getzep.com/facts ／ https://github.com/getzep/graphiti

### Graphを新しいSource of Truthにしない

既存の`skills/graph-engineering/SKILL.md`は、**Graphは問いに答えるためのProjectionであり、外部効果の権威ではない**と明記している。以下を守る：

- Append-onlyの元記録、元の証拠リンク、実行主体、記録時点を保持。
- 同じ元記録からGraphを何度でも再現できること。
- 自動の「関係の推測」は`inferred`のまま、`verified`へ格上げしない。
- Graphの上の`authorized`は外部アクションの許可ではない。
- 何が変わったかの理由と原記録を追跡可能にする。
- 権利・本人の同意・撤回はGraphと別の実行ゲートで確認。
- 本番に新Graph DBを導入するのは、性能測定で必要な時だけ。

## 5｜通信と実行は別レイヤー：MCPとA2A

**MCP**はリソース、プロンプト、ツールをAIへ公開するためのプロトコル。2026-07-28版の仕様はstateless coreや認可強化などを導入。MCPのtoolを発見したことは、そのtoolを任意に実行してよいという意味ではない。host・provider側の許可が必要。

出典：https://modelcontextprotocol.io/specification/2026-07-28 ／ https://blog.modelcontextprotocol.io/posts/2026-07-28/

**A2A（Agent2Agent）**は別のエージェント間のTask／Message／Artifact／Agent Card等を標準化する。これは相互通信の契約で、心的状態のOntologyや外部介入の正しさを保証しない。

出典：https://a2a-protocol.org/latest/specification/

**OpenTelemetry**は、エージェント・ツール・実行・遅延等の観測性を支える。2026年時点のGenAI agent semantic conventionsのステータスには`Development`が含まれ、要件として慎重に版を固定する必要がある。

出典：https://opentelemetry.io/docs/specs/semconv/gen-ai/

**LangGraphやGraphiti**はcheckpoint／時間付きGraphの参照実装として候補。ただし、すでに稼働している`manager_core`と既存ledgerを丸ごと置き換える根拠はない。

出典：https://docs.langchain.com/oss/python/langgraph/persistence ／ https://github.com/getzep/graphiti

## 7｜最小表現：何のノードと関係だけ持つか

最初はコンピテンシー・クエスチョン（システムが答えたい問い）を定義する。

| 問い | 必要な情報 |
|---|---|
| なぜその人の状態がそう推定された？ | 観測・出典・時刻・推測の不確実性 |
| どの介入を提案し、何と比較した？ | 介入ID・対照NO_ACTION・推定対象・モデル版 |
| 実際に何が送られ、どう確認された？ | 独立レシート・実行ID・verifyの出典 |
| 何が変わったと測定できた？ | 結果の観測値、単位、測定窓、前後、比較群 |
| 予測時点で本当に知っていた事実は？ | valid time と recorded timeの両方 |
| 許可・同意・撤回は有効？ | **必ず実行系の正規権限から再チェック**。グラフの記述から決めない |

最初のGraphは`Subject/Goal/Observation/Action/Receipt/Outcome`と少数の辺（`HAS_GOAL`、`HAS_OBSERVATION`、`PROPOSED_ACTION`、`RECEIPT_FOR`、`INDEPENDENT_READBACK_FOR`、`SUPERSEDES`）のプロジェクションでよい。

これらの**大文字predicateはManagerの教育用ローカル語彙**であり、W3C公式のOntologyに既にある定義を名乗ってはいけない。将来必要ならPROV-OやBCIOの該当クラス・関係へ対応を定義する。PROV-OとJSON-LDを使えば、汎用データ連携へ拡張できる。

### 例：同じ「通知」という行動でも5段階を区別

1. **Model inference**：通知すると完了率が改善しそう（推測）。
2. **Proposal**：通知する候補を生成（まだ実行していない）。
3. **Provider receipt**：外部実行系が送信を受理した可能性を示す（相手が受信・行動した証拠ではない）。
4. **Independent readback**：実行とは別の観測系が結果を確認した（観察がある）。
5. **Causal effect**：適切な対照・識別・統計により**通知が原因でどれくらい改善したか**を推定する（readback単独では到達しない）。

たとえば通知が送信でき、タスクも完了した事実があっても、その通知が完了の原因だったとは限らない。

## 8｜再現した教育用コード：バイテンポラルGraph Projection

`experiments/p05_1_ontology_readonly.py`では、以下を実装・実行：

- **5件の完全人工イベント**を入力し、出典IDとSHA256、観測時刻／記録時刻／事実の適用時刻を保持。
- `project(events, knowledge_cutoff=...,world_time=...)` で、その時点で知られ得た情報だけを可視化。
- `model_inference`は`INFERRED_NOT_VERIFIED`を保つ。
- `provider_receipt`は`PROVIDER_RECEIPT_NOT_OUTCOME`を保つ。
- `independent_readback`は実行主体とは異なる観測者が必要（ただし教材内の識別子であり真正の独立性まで保証しない）。
- 重複IDによる異なる主張、実世界の個人ID、未知の関係、秘密・私的クラスを拒否。
- 既存の`StateMachine`と`InterventionPlan`をimportし、**因果効果が証明できないときはNO_ACTION**を選ぶ。
- `as_jsonld` でRDF/PROV-Oを参照する相互運用の雛形を出力。完全なOWL推論・SHACL意味検証は実装していない。
- **26テスト成功**。Graphに`can_authorize_execution=false`、`can_prove_real_world_effect=false`を明示する。

結果：`evidence/P05-1_READONLY_SYNTHETIC_PROJECTION.json`。再現ログ：`evidence/P05-1_UNIT_TESTS.txt`。

このコードは**GraphitiやNeo4jを新規導入しない**。ノード数や頻度・並行更新に具体的な負荷が確認されるまで、単純なread-only JSON投影で十分。実際の公式レシートやユーザー状態への接続はここでは行っていない。

## 9｜最も危険な誤解：Digital Twinを「人間の真実」だと思うこと

2026年の独立研究*Digital twins are funhouse mirrors*は、事前登録した19研究・164結果について、実在の個人回答とLLM digital twinsの回答を比較した。個人差の相関平均は約**0.20**で、個人差不足・ステレオタイプ・代表性バイアス・思想上の偏り・過度の合理化などを挙げた。**この研究が全てのDigital Twinを否定するわけではないが、プロンプトに人格情報を増やすだけでは忠実な個人模型にならない**という厳しい証拠。

出典：https://pmc.ncbi.nlm.nih.gov/articles/PMC13537255/

Managerの模型は個人・集団・領域ごとに、見かけの自然さとは別に、校正、未見回答、介入効果、意思決定価値を検証する必要がある。

## 10｜P05-1の学習・実装に対する具体的な評価基準

まず実験前に30〜100件程度の合成イベントケースを固定し、**flat JSON検索／既存の個別ツール照会／軽量graph投影**を同じ問いで比較する。Graphが有益か証明できなければグラフDBの導入も急がない。

| テスト指標 | 何を測るか |
|---|---|
| Provenance completeness | ノード/辺に根拠・出典・時刻がある割合 |
| Temporal validity | 後知恵・未来情報リークを拒否できた割合 |
| Identity correctness | 別人・同じ人・同名の混同と誤融合 |
| Epistemic correctness | 「推測」「観測」「receipt」「効果」を誤昇格しなかった割合 |
| Authorization boundary | Graphが実行権限を発行・継承してしまわないこと |
| NO_ACTION support | 検証不足なら何もしない方策が残ること |
| Query correctness | 定義済み6個の問いに対する正答・根拠・未知を出せるか |
| Replay determinism | 元レコード順や重複に依存せず同じ投影を再生成する |
| Latency & cost | Flatな方法と比較した遅延・記憶・トークン費用 |
| Generalization | 新しい対象・時期・アプリ・研究に意味を移植できるか |

本講の人工26テストは主に型・境界・決定性を確認するもので、上記すべての定量ベンチマークや現実世界での正答率・改善効果が確認されたわけではない。

## 11｜P05-2へ進む時に固定すべき設計判断

P05-1の段階で必要な**設計上の結論**は以下。

- 予測結果と観測結果を同じ値として扱わない。
- イベントとstateの「意味」と「いつ知っていたか」を区別する。
- PROV-O/JSON-LDを相互運用の参照に、BCIO/BCTを介入語彙の参照に使う。
- 内部正本は既存Manager Coreとruntime ledger、Graphは再生成可能なread-only projection。
- 実行は別の権限機構に委ね、証拠の確認も独立する。
- 最小モデルの手元の成功は実人間のDigital Twin成功と認定しない。

次のP05-2では、**prediction_id、experiment_id、decision_id、action_id、effect_key、receipt_ref、independent_readback_ref、outcome_measure_id、timestamp、model_version、provenance、permission_scope**を結ぶ共通契約を、既存IDと既存schemaの互換性を守って定義・評価する。
