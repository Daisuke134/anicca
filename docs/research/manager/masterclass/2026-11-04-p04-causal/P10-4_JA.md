## 1. 自律運用とは何か
1回の正しい応答ではなく、長期間の業務を安全に継続する能力。ある時点でモデルAPIが落ち、外部サービスのレスポンスが失われ、OSが再起動し、利用者が同意を取り消しても、過去状態・費用・権限・未確定副作用を復元できることが必要。

**Reliability（要求通り動く）**、**Recoverability（失敗しても正しく立て直す）**、**Sustainability（収益・現金・安全を維持する）**、**Autonomy（隠れた人手を計測する）**は別軸の測定である。

## 2. 現場のDurable Execution
Temporal/Cadence等のDurable Workflowは、ステップ履歴を保存し、worker crash後に状態再生して処理を続ける。TemporalのWorkflowには決定論的コードを置き、外部APIやランダムなLLM推論はActivityとして実行する。Activityにはタイムアウト、リトライ、ハートビートがある。
- Temporal durable execution overview: https://docs.temporal.io/evaluate/understanding-temporal
- Temporal error handling/Activity idempotency: https://docs.temporal.io/develop/python/best-practices/error-handling
- Temporal design patterns: https://docs.temporal.io/design-patterns

**最大の落とし穴**：workerが外部送金を送った直後にクラッシュすると、Temporal側には成功が記録されず、Activityが再実行されることがある。「Temporalを採用した＝外部副作用がexactly-once」ではない。providerが信頼できるidempotency keyを実装している場合にのみ安全な重複排除が期待できる。プロバイダの仕様/期限/効果identityを確認し、UNKNOWNはread-only reconciliationへ送る。

Manager Coreは既にDurableOutbox/Effect、reconcile、UNKNOWN_EFFECT、independent verifierを持つ。今すぐ別のワークフローDBへ移行するのではなく、今のエフェクト境界を守り、欠けた再開・監視だけ追加する。

## 3. 仕事の状態機械
以下の型を曖昧な自然言語ではなく、programmatic stateとして区別：
OBSERVED → HYPOTHESIZED → PROPOSED → RISK_CHECKED → AUTHORIZED → EXECUTED → VERIFIED → EVALUATED → LEARNED。
分岐：NO_ACTION、REJECTED、UNKNOWN_EFFECT、MEASUREMENT_MISSING、ROLLBACK_REQUESTED、ROLLED_BACK。

AUTHORITYはManager Core内のテストfixtureだけで本番許可にはならない。Providerの「処理しました」はVERIFIEDとは異なり、独立なreadbackが必要。過去の効果が不明ならUNKNOWNを保持し、**自動再送禁止**。

## 4. 計測・SLO・Error Budget
SREの実務では、Service Level Indicator（SLI：実測信頼性）とObjective（SLO：目標）を設定する。

SLI = valid verified operations / eligible operations.
Error Budget = (1−SLO) × eligible operations − actual failures.

仮に1,000件の仕事で99.5% SLOなら、許容失敗は5件。失敗3件なら残り2件、失敗6件なら超過。これは教育用の数字であり、実際のManager本番SLOを決定したものではない。

Google SRE Workbookは、SLOに紐づいたerror budget policy（いつ新機能リリースを止めて信頼性へ集中するか）や、多時間窓のburn-rate alertingを示している。
- https://sre.google/workbook/implementing-slos/
- https://sre.google/workbook/alerting-on-slos/

Managerで監視する候補：**externally verified completion rate**、UNKNOWN_EFFECT backlog age、policy-denial rate、receipt/readback lag、cost per verified success、real cash runway、refund/chargeback、harm/complaint、human rescue rate、fraud/unauthorized effects。
指標とカウントの欠測割合、業務種類別の重み、閾値の根拠も明示。成功率だけを上げようとして有害な実行を奨励しない。

## 5. 安定運用の業務サイクル
### 常時：Admission（入場制御）
入力→最小権限→同意→予算予約→安全性→有効な期限→実行可否判定。通らなければNO_ACTION。ポリシー決定の時点と証拠版を保存。開発者/モデルが勝手に自分へ権限を付けられないようにする。

### 実行：Outbox / Dispatch
effect_keyの重複を排除。送信intentを先に永続化し、非冪等な操作の曖昧なタイムアウトはUNKNOWNとして再送停止。read-only APIでは上限付きbackoffで再試行可。

### 検証：Reconcile / Readback
provider receiptの有無だけでは成功認定しない。別チャネルから実際の結果を確認し、遅延・不一致・返金を修正履歴として残す。独立観測が取れない場合はNOT_VERIFIED/MEASUREMENT_MISSING。

### 学習：Evidence Store
許可が明示されている場合に限り、権限・時点・データライセンスを保ったままモデル学習へ渡す。実行の結果から因果効果を勝手に認定しない。

## 6. Financial sustainability：自己資金化の定義
キャッシュが減っていないように見えること、トークンが無料だったこと、売上が1件あったことは自己資金化ではない。
少なくとも以下を別々に確認：
- cash in/out、銀行・決済プロバイダの着金/出金証拠
- recognized revenue、返金、chargeback
- provider bill / credits / variable cost / fixed operating expense
- period contribution margin、operating profit、cash runway
- independent customer value/retention、harm monitoring
- all human-assist work including external contractors and mandated oversight

Runway (months) = available unrestricted cash / positive monthly net cash burn. 月間ネットバーン≤0なら「無限月数」ではなく、別の収支・季節性・債務を監視する。

**資金繰りの正本は本来の会計・銀行・支払プロバイダ。** P10-1のread-only projectionへ流すだけ。未照合・欠測の費用は利益に計上しない。

## 8. CI/CD・変更管理・リリース
本番変更は小さな単位で、固定テスト・セキュリティ/ライセンス検査・credential scoping・影響試算・段階公開・公式readback・ロールバック計画に通す。独立の証拠が無ければmainへのマージや本番の成功を主張しない。
モデルバージョン・prompts・toolsの更新は、固定benchmark/安全試験/経済性を比較し、可能なら段階ロールアウトとholdoutで差を測定する。全エージェントを一斉に書き換えない。
