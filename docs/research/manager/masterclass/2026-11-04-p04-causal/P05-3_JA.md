# P05-3｜複数エージェント・ホストの担当と実行権限

**2026-11-04 / 講義・既存コード読解・人工実行・単体テスト完了。実サービスへの権限発行は未実施。**

## 1. 何を解決するか

現状のManager構想には、What-ifモデル、GPT/Grok/Muse/Codexなどの実行担当、各サービスのAPI、外部の独立検証がある。これらが混線すると「Plannerが正しいと判断した」という発言が「実行してよい」に格上げされ、重複送信・資金移動・望まない介入につながる。

**役割の分離**：
- **Observer**：権利のある情報だけを収集し、何を観測できたかを記録。推測した心理状態を真実へ昇格させない。
- **Planner / What-if**：候補を生成し、結果や不確実性を予測。実行権限は持たない。
- **Policy**：便益・費用・負担・同意などを比較し、NO_ACTIONも正式な選択肢として評価。
- **Authority issuer**：実際の主体とスコープ、期限、撤回、費用上限を検証する独立した許可機構。LLMに委譲しない。
- **Executor**：許可された操作を一意のIDで実行し、重複と不明応答をOutboxへ記録。
- **Verifier / Evaluator**：Executorと独立の観測源で実際の操作と結果を調べ、因果効果の測定はさらに対照設計へ依存。

既存MCPなどの通信仕様でツールが見えることと、ツールを実際に使えることは異なる。APIキーの所有も正規の本人同意や費用権限と同じではない。

## 3. 最小の権限モデル

```python
authority = AuthorityVerifier({"synthetic-issuer": fixture_key})
grant = Grant(
    grant_id="grant-synthetic-01",
    issuer="synthetic-issuer",
    domain="opportunity",
    action="synthetic_observation",
    target="synthetic:target-0001",
    limit=0.05,
    not_before=START,
    expires_at=END,
)
signature = authority.sign_for_fixture(grant)
authority.authorize(grant, signature, "opportunity",
                    "synthetic_observation", "synthetic:target-0001",
                    0.01, NOW)
```

- `AuthorityVerifier`：事前に信頼した署名発行者に限定する検査器。
- `Grant`：許すdomain/action/target/金額/時間を固定したデータ。
- `sign_for_fixture()`：本物の権限発行ではなく、教育用の人工署名。
- `authorize()`：予定操作と固定スコープを比較し、署名や期限、撤回を検証。
- 本番では本人または適切な事業主体からの事前同意、サービス認証、必要な審査、監査・停止を別の正規機構で担う。

**実行結果**：テスト用に正しい権限で`True`、違うターゲット・違う領域・予算超過・不正署名・期限切れ・失効の6種類は全て`PermissionError`で拒否。Plannerには本物の鍵や実行権限を付与していない。

## 4. 複数エージェントの契約

Managerを司令塔にし、GPT/Grok/Muse/Codexを候補生成・コード作成・調査・実行補助として使うことは可能。ただし「担当者のエージェント名」では権限は認定できない。

ツール呼出しごとの本番要求は少なくとも次を正規データと照合すべき：actor identity（ユーザー本人か、サービス主体か）、tenant、issuer、purpose、object/action/target、許されたデータ、期限、上限費用、操作の可逆性、idempotency key、監査参照、撤回状態。

**No human in every loop**を目指すことと、本人に知らせず精神状態を測定・介入したり、外部サービスの規約・認証を無視することは別。許可済みの低リスク範囲に限り、各回の再承認なしの自律実行を検討する。
