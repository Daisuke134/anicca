# x402 v1/v2 互換性ベストプラクティス調査（2026-07-17）

調査方法: ctx7 CLI（`/coinbase/x402` docs）+ `crwl`（x402.org系 raw docs, x402scan.com）+ `gh api`（coinbase/x402 実ソース）。WebSearch/WebFetch は不使用。

## 核心の問い: v2 seller は v1 クライアントの支払いを受けられるか

**答え: No（デフォルト実装では受けられない）。ドキュメント上の「後方互換」表現と、実装のデフォルト挙動は一致しない。**

### 根拠1: 公式 migration guide の記述（一見 Yes に読める）
> "The facilitator supports both V1 and V2 protocols. During migration, your V2 server can still accept payments from V1 clients, but we recommend updating clients to V2 for full feature support."
出典: `github.com/coinbase/x402/blob/main/docs/guides/migration-v1-to-v2.mdx`（"Mixed V1/V2 compatibility" セクション、ctx7 `/coinbase/x402` 経由・crwl で原文確認済み）

ただしこの文は **facilitator（verify/settle バックエンド）が両バージョンのプロトコルを喋れる** という意味であり、seller ミドルウェアが 402 チャレンジを v1/v2 両形式で返す、という意味ではない。

### 根拠2: 実ソースコードで反証（`@x402/express@2.x` のデフォルト挙動）
`x402HTTPResourceServer.ts`（`typescript/packages/core/src/http/x402HTTPResourceServer.ts`, `coinbase/x402` main）の `createHTTPResponse()`:
```ts
const response = this.createHTTPPaymentRequiredResponse(paymentRequired);
// Use callback result if provided, otherwise default to JSON with empty object
const contentType = unpaidResponse ? unpaidResponse.contentType : "application/json";
const body = unpaidResponse ? unpaidResponse.body : {};
return { status, headers: { "Content-Type": contentType, ...response.headers }, body };
```
`accepts`（支払いオプション配列＝v1 クライアントが body から読む情報）は **`response.headers` に base64 エンコードされた `payment-required` ヘッダとしてのみ**入り、`body` はデフォルトで空オブジェクト `{}`。v1 互換の body を返したい場合は seller が `unpaidResponseBody` コールバックを自前実装する必要がある（デフォルトでは無い）。

### 根拠3: 自分のリポジトリでの実測（本番同等環境、2026-07-17）
`/Users/anicca/anicca-project/docs/superpowers/plans/2026-07-17-x402-v2-migration.md` Task4 Step2（franklin2 実HTTP検証）:
> "★発見: `buyer-cdp.mjs`(x402-fetch@1.2.0, v1 client)は v2 seller に払えない。v2 の `@x402/express@2.17.0` は payment requirements を JSON body でなく `payment-required` ヘッダに載せる(body は `{}`) — x402-fetch@1 は body の `accepts` をパースする実装のため `TypeError: Cannot read properties of undefined (reading 'map')` で即死。"

コード側の分析（根拠2）と実測（根拠3）が完全一致。ドキュメントの「Mixed compatibility」は facilitator 層の話に限定され、デフォルトの seller ミドルウェアには v1 buyer への自動フォールバックが無い。

## 逆方向: v2 クライアントは v1 seller に払えるか → Yes（実装確認済み）
`typescript/packages/http/fetch/src/index.ts`（`@x402/fetch@2.18.0`, `wrapFetchWithPayment`）:
```ts
// Try to get from headers first (v2), then from body (v1)
let body: PaymentRequired | undefined;
...
paymentRequired = httpClient.getPaymentRequiredResponse(getHeader, body);
```
v2 の公式買い手クライアント (`@x402/fetch`) は 402 応答を **まずヘッダ（v2）、無ければ body（v1）** の順で解釈する実装になっており、v1 seller にも v2 seller にも支払い可能（前方＋後方互換）。買い手側だけが両対応。

サーバー側の `paymentHeader` 読み取りも `payment-signature`（v2）と `x-payment`（v1）両方を見る（`typescript/packages/http/express/src/index.ts`: `adapter.getHeader("payment-signature") || adapter.getHeader("x-payment")`）が、v1 クライアントは前段のチャレンジ解釈（body）で失敗するため、この分岐に到達する前に死ぬ。

## 本番 seller の v1/v2 分布
- x402scan.com のフィーチャード一覧（`crwl https://www.x402scan.com`）で "Otto AI x402" の説明文に **"74 pay-per-call AI services on x402 V2"** と明記 — 実運用 seller が v2 を掲げている実例（出典: x402scan.com トップページ、featured services 表）。
- x402scan の登録ページ（`www.x402scan.com/resources/register`）自体には v1/v2 の明示要件は無い（URL 登録のみ）。「v2 必須」の記述は確認できず。
- 自リポジトリの実測（同 plan doc Task4 Step5）: x402scan の Bazaar discovery クロールで v1 seller（claude-p, `serve.mjs`）は 8/8 商品が discoverable、v2 seller（franklin2, `serve-v2.mjs` + `discoverable:true`）は 1/8 のみ（実決済後の事後登録と推定）。**`discoverable` フラグだけでは v2 の proactive discovery が機能していない**ことをこのセッションで実測済み。`@x402/extensions` の `declareDiscoveryExtension`（bazaar 拡張）への切替が未検証の次アクションとして plan doc に残っている。

## ベストプラクティスの推奨

1. **新規 seller は v2（`@x402/express` 等）で実装する。** v1 パッケージは事実上凍結（1.2.0 止まり）、v2 が開発ライン。
2. **v1 買い手を失うリスクは実在する。** デフォルト v2 ミドルウェアは v1 buyer に対して 402 body が空 `{}` になり即死する。v1 buyer 互換を維持したいなら `unpaidResponseBody` コールバックで v1 形式の `{ x402Version: 1, accepts: [...] }` body を手動で組んで返す実装が必要（コードには存在するが自動ではない＝要実装）。
3. **移行期は v1/v2 の2ルートを並存させるのが安全（このプロジェクトが実際に採用した設計）。** `serve.mjs`（v1, legacy パッケージ）と `serve-v2.mjs`（v2）を別ファイルで維持し、店ごとに段階的に切替える。稼ぎ頭（claude-p）は最後に切替。
4. **x402scan discoverability は v2 化しただけでは担保されない（実測 FAIL）。** v2 化と同時に Bazaar 拡張（`declareDiscoveryExtension`）まで実装しないと、v1 時代にあった全商品カタログ露出が失われる。v2 移行のチェックリストに「Bazaar 拡張確認」を必須項目として含めること。
5. 買い手側は `@x402/fetch`（v2 クライアント）で統一してよい。v1/v2 両 seller に自動対応するため、買い手の二重実装は不要。
